# Development

How the code is organised, how to work in development mode and how to run
the checks. Setting up from scratch is described in
[INSTALLATION.md](INSTALLATION.md); the architecture in
[ARCHITECTURE.md](ARCHITECTURE.md).

## Repository layout

```text
backend/
  app/
    api/v1/        routers (thin), one file per area
    modules/       business logic per domain (models, schemas, services)
    core/          settings, security, errors, logging, rate limits, mailer
    db/            engine, sessions, base model
    worker/        background jobs (python -m app.worker)
    seeds/         python -m app.seeds base|demo
    cli/           python -m app.cli create-admin
    main.py        application factory
  alembic/         migrations 0001…0009
  tests/           pytest
  pyproject.toml, uv.lock, Dockerfile (targets: dev, prod)
frontend/
  src/
    app/           providers, store, routers, layouts
    pages/         route pages
    features/      domain features (RTK Query slices, components, hooks)
    shared/        API base, UI kit, i18n (ru, ky, uz), generated API types
    styles/        Tailwind v4 tokens and global CSS
    test/          Vitest setup, fixtures and mocks (incl. Telegram)
  nginx/default.conf   nginx config of the demo image
  package.json, package-lock.json, vite.config.ts, Dockerfile (targets: dev, build, demo)
infra/postgres/initdb.d/   empty init directory (PostGIS comes from Alembic)
docs/                      specifications and the decision log
compose*.yaml              Docker Compose: shared, dev, demo, sandbox
```

## Rules of the project

The working rules are in [`CLAUDE.md`](CLAUDE.md); the decision log
[`docs/DECISIONS.md`](docs/DECISIONS.md) has priority over other documents.
In short:

- Thin routers, business logic in services; check authorization and
  ownership on the backend; never trust client prices, roles or totals.
- Schema changes only through Alembic migrations.
- Frontend: RTK Query for every API call, i18next for every text,
  React Hook Form + Zod for forms; handle loading, error, empty and success
  states; mobile, tablet and desktop; visible keyboard focus.
- No new dependencies without an approved decision (DEC-02, DEC-94).
- Never log passwords, tokens, secrets, `initData` or card data.

## Development mode

```bash
DC="docker compose -f compose.yaml -f compose.dev.yaml"
$DC up --build -d
$DC logs -f backend
```

- Backend: Uvicorn with `--reload`; `./backend` is mounted into the
  container.
- Frontend: Vite dev server; `./frontend` is mounted, `node_modules` stays
  inside the container. File watching uses polling (`VITE_USE_POLLING`)
  because Docker Desktop on Windows does not forward file events reliably.
- Dev ports (all on `127.0.0.1`): 5173 frontend, 8000 backend,
  5432 main DB, 5433 test DB, 8025 Mailpit.

### Migrations

```bash
$DC exec backend alembic upgrade head
```

Revision ids are readable names (`0009_telegram_only_accounts`, with
`down_revision = "0008_notifications"`); a new migration follows the same
`000N_<name>.py` pattern and is written by hand, never generated by
`create_all()`.

The migration cycle (`upgrade → downgrade → upgrade`) is covered by
`backend/tests/test_migrations.py`.

### Dependencies

- Python: `uv` with `backend/uv.lock`; images install with
  `uv sync --frozen`. To add an approved package:
  `$DC exec backend uv add <package>`, then commit `pyproject.toml` and
  `uv.lock`.
- Frontend: `npm` with `frontend/package-lock.json`; images install with
  `npm ci`.

### API types for the frontend

The frontend types are generated from the running backend's OpenAPI schema:

```bash
$DC exec frontend npm run gen:api     # writes src/shared/types/openapi.ts
```

## Checks

### Frontend

Run inside the running `frontend` container:

```bash
$DC exec frontend npm run typecheck
$DC exec frontend npm run lint
$DC exec frontend npm run format:check
$DC exec frontend npx vitest run --maxWorkers=1
```

- `--maxWorkers=1` keeps memory low on Docker Desktop. The full suite
  (36 files, 556 tests) takes about 15 minutes on a loaded laptop; you can
  also run one file or folder, e.g. `npx vitest run src/features/telegram`.
- `vite.config.ts` sets `testTimeout: 15000`; `src/test/setup.ts` sets the
  Testing Library wait to 5 s. The first render of a test file is slow in
  containers on Windows — do not raise limits to hide a real problem.
- The Telegram Mini App is tested with a fake `window.Telegram`
  (`src/test/telegramMock.ts`) and a fake `fetch` router
  (`src/test/fetchRoutes.ts`); no bot token exists in the frontend.

Production build check without touching `frontend/dist`:

```bash
$DC exec frontend sh -c 'npx tsc -b && npx vite build --outDir /tmp/dist-check --emptyOutDir'
```

### Backend

Lint and format (no database needed):

```bash
$DC run --rm backend ruff check .
$DC run --rm backend ruff format --check .
```

Tests:

```bash
$DC exec backend python -m pytest
```

- In dev mode `TEST_DATABASE_URL` points to `db-test` (data in tmpfs,
  discarded when the container stops). Tests marked `db` are skipped when
  `TEST_DATABASE_URL` is not set.
- The suite refuses to run unless the test database name ends with `_test`
  and differs from `DATABASE_URL`, so it can never touch the main database.
- The full suite takes about an hour; migration tests dominate. Run a single
  file while working, e.g. `python -m pytest tests/test_cart_api.py`.
- In the author's long-running environment, backend tests of later stages
  ran on separate stage databases in `db-sandbox` instead of `db-test`
  (DEC-152 п. 12); for a fresh clone the `db-test` default above is enough.

### What is not covered yet

- No end-to-end browser tests (Playwright is planned for stage 11); the
  critical scenarios are listed in `docs/DEVELOPMENT_PLAN.md`, stage 11.
- The Mini App inside a real Telegram client is checked manually (see
  [DEPLOYMENT.md](DEPLOYMENT.md)).

## Conventions

- Languages: every UI string exists in `ru`, `ky` and `uz`
  (`frontend/src/shared/i18n/locales/*/common.json`); a test checks that the
  three files have the same keys.
- Design tokens live in `frontend/src/styles/tokens.css`; components use
  Tailwind utilities over these tokens, not raw colours.
- Line endings and formatting: Prettier (frontend), Ruff (backend),
  `.gitattributes` at the root.
