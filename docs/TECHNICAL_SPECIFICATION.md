# TECHNICAL_SPECIFICATION.md

## Назначение

Демонстрационный адаптивный сайт доставки еды одного ресторана и одного
филиала в Оше, Кыргызстан. Архитектура должна позволять адаптацию под
реального клиента.

Клиентских интерфейсов два (DEC-142, DEC-144): сайт в браузере и
Telegram Mini App (маршруты `/tg/*`, DEC-152). Оба используют общий
backend, API `/api/v1` и бизнес-логику; у каждого отдельные критерии
приёмки.

Утверждённые решения фиксируются в `docs/DECISIONS.md` (ссылки
`DEC-NN`). При расхождении между документами приоритет имеет
`DECISIONS.md`.

## MVP

Клиент просматривает меню, выбирает варианты и добавки, сохраняет
адреса, оформляет доставку или самовывоз, отслеживает статус заказа и
отправляет запрос на отмену. Персонал управляет каталогом, заказами,
зонами и курьерами. Есть внутренние уведомления клиентам и привязка
Telegram. Тот же покупательский сценарий доступен в Telegram Mini App:
вход по проверенному `init_data`, явная регистрация нового клиента или
привязка существующего аккаунта сайта по email и паролю (DEC-152).
Оплата: наличные или демонстрационная mock-card без списания денег.

Не входят: несколько филиалов, реальные платежи, промокоды, live GPS
курьера, складской учёт, микросервисы, подтверждение email, гостевая
корзина, уведомления сотрудникам, Telegram webhook.

## Роли

-   `customer`: каталог, корзина, адреса, свои заказы, запрос отмены,
    уведомления. Выдаётся при регистрации на сайте или в Telegram Mini
    App (DEC-24, DEC-152). Mini App доступен только этой роли (DEC-142).
-   `admin`: полный административный доступ.
-   `cook`: ограниченный доступ к кухонным заказам и статусам через
    admin UI (только `/staff/kitchen/*`, без телефона и адреса клиента,
    DEC-25).
-   `courier`: отдельный мобильный кабинет и только назначенные заказы.

Роли сочетаются: сотрудник может также иметь роль `customer` (DEC-23).
Сотрудников создаёт администратор с временным паролем; при первом входе
сотрудник обязан сменить пароль (DEC-28). При выдаче роли `courier`
автоматически создаётся профиль курьера (DEC-27); роль нельзя снять,
пока есть активные назначения (DEC-29). Пользователи с историей заказов
не удаляются, а деактивируются (DEC-62).

Первый администратор создаётся только CLI-командой
`python -m app.cli create-admin`: интерактивный ввод имени, email и
пароля (дважды, без отображения), работает только при отсутствии
администратора, защищена от параллельного запуска; создаёт
пользователя только с ролью `admin` (DEC-113); стандартных учётных
данных нет (DEC-88).

Политика паролей --- единая для всех сценариев: 8–128 символов, минимум
одна буква и одна цифра (DEC-96). Телефон --- формат Кыргызстана `+996`
и 9 цифр; backend нормализует ввод и хранит `+996700123456` (DEC-89).

RBAC и проверка владельца ресурса обязательны на backend; роли и
активность пользователя проверяются по БД на каждом запросе (DEC-66).

Frontend: React, TypeScript, Vite, React Router, Redux Toolkit + RTK
Query, Tailwind CSS, i18next, React Hook Form, Zod. Backend: Python,
FastAPI, Pydantic, SQLAlchemy 2.0, PostgreSQL + PostGIS, Alembic.
Инфраструктура: Docker Compose. Тесты: Pytest, Vitest, React Testing
Library, Playwright. Архитектура: модульный монолит.

Согласованные дополнительные зависимости (DEC-02, DEC-94):

-   backend: `argon2-cffi`, `PyJWT`, `psycopg[binary]` (v3),
    `GeoAlchemy2`, `httpx`, `slowapi`, `Pillow`, `python-multipart`,
    `pydantic-settings`; тесты --- `pytest-asyncio`; качество кода ---
    `ruff`;
-   frontend: `leaflet`, `react-leaflet`,
    `@geoman-io/leaflet-geoman-free` (бесплатная версия),
    `openapi-typescript`; качество кода --- ESLint, Prettier;
-   инфраструктура: Mailpit (перехват email в dev/demo).

Версии фиксируются в lock-файлах. Геометрия и пересечения зон
проверяются на backend через PostGIS, frontend не является доверенным.

## Инфраструктура

-   Единый origin для frontend и `/api/v1`: Vite proxy в `dev`, nginx в

-   Сервисы: PostgreSQL + PostGIS, отдельная тестовая БД с PostGIS
    (DEC-69), backend API (один процесс, один Uvicorn worker, DEC-95),

-   Git инициализируется на Этапе 1, `.gitignore` исключает `.env`,
    локальные БД, volumes, кэши и build-артефакты (DEC-05).

## Основные правила

-   API prefix `/api/v1`.
-   UUID для основных идентификаторов (генерирует PostgreSQL, DEC-63).
-   KGS; деньги `NUMERIC(12,2)`, не float.
-   Хранить timestamps в UTC (`TIMESTAMPTZ`), отображать время ресторана
    в `Asia/Bishkek`.
-   Языки: `ru`, `ky`, `uz`; переводы сущностей --- в отдельных
    translation-таблицах. Fallback: запрошенный язык → язык пользователя
    → `ru` → первый доступный.
-   Пароли --- Argon2id.
-   Access JWT короткоживущий (15 минут), на frontend хранится только в
    памяти; refresh token хранится в HttpOnly cookie сроком 30 дней;
    флаг `Secure` устанавливается при `APP_ENV=demo` и не
    устанавливается при `APP_ENV=dev` или `APP_ENV=test` (DEC-68,
    DEC-140); rotation, строгий отзыв всей семьи при повторном
    использовании без льготного окна; конкурентный refresh между
    вкладками координируется через `navigator.locks`; в БД хранить
    только hash (DEC-65, DEC-80, DEC-110).
-   CSRF: единый origin, проверка `Origin` и специального заголовка
    (DEC-68); ошибка --- `CSRF_FAILED`.
-   Login не раскрывает существование или неактивность аккаунта
    (DEC-103); сброс пароля всегда отвечает одинаково (DEC-108).
-   Telegram Mini App (DEC-142, DEC-152): `init_data` проверяется на
    backend до использования; выдаётся только access JWT без
    refresh-cookie; при входе без связи аккаунт не создаётся автоматически
    --- клиент выбирает регистрацию или привязку аккаунта сайта по email и
    паролю; один Telegram-аккаунт связан не более чем с одним
    пользователем и наоборот; перенос связи и слияние аккаунтов не
    выполняются.
-   Rate limits (DEC-80, значения в конфигурации): login и привязка из
    Mini App --- общий счётчик 5/мин на IP; вход и регистрация в Mini App
    --- отдельный счётчик 5/мин на IP;
    запрос сброса пароля 3/час на аккаунт и IP; API 120/мин на
    пользователя; публичные endpoints 60/мин на IP. Счётчики `slowapi` в
    памяти; при нескольких процессах --- Redis-backed limiter (DEC-95).
-   Все цены, права, доставка и переходы статусов проверяются
    backend-ом. Все расчёты стоимости --- только на backend в едином
    модуле (DEC-08).
-   Заказ сохраняет snapshots названий, вариантов, групп модификаторов,
    модификаторов, цен, адреса и стоимости доставки на языке клиента
    (DEC-15, DEC-16, DEC-60).
-   Оформление заказа транзакционное и идемпотентное (`Idempotency-Key`,
    ключи хранятся 24 часа, DEC-59).
-   PostGIS используется для полигонов зон доставки; Docker image должен
    включать PostGIS.
-   Изображения хранятся в локальном volume, в БД --- путь/storage key.
    Разрешены JPEG, PNG, WebP до 5 МБ, содержимое проверяется (DEC-70).
-   Ошибки API --- в едином формате (DEC-73).

## Каталог

Категории: пицца, бургеры, шаурма, картофель фри, курица, напитки,
десерты, комбо. Размеры --- `product_variants`; у каждого товара
минимум один вариант, у простых --- «Стандарт», `base_price` нет
(DEC-06). Ингредиенты и дополнительные опции ---
`modifier_groups`/`modifiers`. У групп есть required/min/max selection;
min/max считают число разных выбранных модификаторов. Модификатор
можно выбрать в количестве до `max_quantity` (по умолчанию 1), например
двойной сыр (DEC-07, DEC-81). `variant_modifier_prices` может
переопределять доплату модификатора для варианта. Удаление категории ---
деактивация (DEC-26).

## Корзина

Корзина хранится в PostgreSQL, одна активная корзина на пользователя с
ролью `customer`. Гостевой корзины нет: «В корзину» без входа ведёт на
вход с возвратом к товару (DEC-13). Одинаковые позиции (товар, вариант,
модификаторы с количествами, пожелания) объединяются (DEC-11).
Изменяются только количество и пожелания (DEC-12). Цены корзины
пересчитываются сервером при каждом чтении.

## Заказ

При оформлении backend заново загружает каталог и пересчитывает цены.
Клиент передаёт `expected_total` только для сравнения; при расхождении
сервер возвращает `409 PRICE_CHANGED` и актуальный расчёт (DEC-09,
DEC-10).

Проверки при оформлении:

-   рабочие часы ресторана; вне рабочих часов заказы не принимаются;
    поддерживаются ночные интервалы (DEC-20, DEC-21);
-   флаги `delivery_enabled` / `pickup_enabled` (DEC-22);
-   доставка: координаты обязательны (точка на карте Leaflet/OSM плюс
    текстовый адрес, DEC-01), зона, стоимость доставки;
-   минимальная сумма: для доставки --- минимум зоны, если он больше 0,
    иначе глобальный; для самовывоза --- глобальный; сравнивается с
    subtotal без доставки (DEC-17–DEC-19).

Самовывоз не требует адреса. Номер заказа --- `OSH-000123` из
PostgreSQL sequence (DEC-14).

### Статусы

-   Доставка: `pending → confirmed → preparing → ready_for_pickup →
    out_for_delivery → completed` (DEC-30).
-   Самовывоз: `pending → confirmed → preparing → ready_for_pickup →
    completed` (DEC-31).
-   `rejected` --- только из `pending` (DEC-32).
-   `cancelled` --- из `pending`, `confirmed`, `preparing`,
    `ready_for_pickup`; после `out_for_delivery` отмена невозможна
    (DEC-33).
-   Администратор подтверждает заказ и завершает самовывоз; повар
    переводит в `preparing` и `ready_for_pickup`; курьер --- в
    `out_for_delivery` и `completed` (DEC-34–DEC-37).
-   Администратор может выполнить курьерские переходы как
    административное вмешательство: обязательный комментарий, запись в
    истории с признаком вмешательства, администратором и временем;
    ограничения state machine сохраняются; для `out_for_delivery` нужно
    активное назначение курьера; фиктивный `accepted_at` не
    записывается (DEC-91).

Полная таблица переходов --- `DATABASE_SCHEMA.md` §7.1.

### Отмена

Клиент не отменяет заказ напрямую, только создаёт cancellation request
в статусах `pending`, `confirmed`, `preparing` (DEC-38); после отказа
может отправить новый (DEC-42). Одобрение запроса, прямая отмена
администратором и отмена по таймауту оплаты выполняются единой
идемпотентной операцией: статус `cancelled` с причиной, запись истории,
возврат успешного mock-платежа (`refunded`, имитация), отмена активного
назначения курьера (DEC-39–DEC-41, DEC-82).

## Оплата

`cash` и `mock_card`. Mock payment всегда симулирован, не собирать номер
карты/CVV/срок действия и не подключать реальный шлюз без отдельного
согласования (DEC-47).

-   `cash`: платёж `pending`, становится `succeeded` при завершении
    доставки курьером или самовывоза администратором (DEC-43).
-   `mock_card`: платёж `pending`; клиент проходит имитацию оплаты;
    при неудаче может повторить (DEC-44, DEC-46). Заказ попадает в
    рабочую очередь и может быть подтверждён только после успешной
    оплаты (DEC-45). Если оплата не завершена за 30 минут, заказ
    автоматически отменяется с причиной `payment_timeout` фоновой
    задачей (DEC-84).

## Доставка

Администратор настраивает полигоны, цену и минимум заказа. Активные
зоны не могут пересекаться по площади; касание границами допустимо
(DEC-53). Демонстрационная зона Оша создаётся seed-скриптом (DEC-76).

Назначение курьера доступно после подтверждения заказа (DEC-48):
ручное или автоматическое по кнопке администратора --- доступный курьер
с наименьшим числом активных заказов в пределах его лимита (DEC-49);
при равенстве --- курьер, которому раньше остальных назначили последний
заказ, затем меньший `user_id` (DEC-151 п. 3). Лимит активных заказов
курьера (`max_active_orders`, 1–10) задаёт администратор (DEC-151 п. 2).
Нет свободных --- `409 NO_COURIER_AVAILABLE` (DEC-50). Переназначение
отменяет старое назначение и создаёт новое (DEC-51); это единственный
способ заменить текущего курьера: автоназначение заказа с активным
назначением ничего не меняет (DEC-151 п. 4). Назначение
выполняется с блокировкой профиля курьера (DEC-67) в едином порядке
блокировок (DEC-151 п. 6). Курьер обязан
принять назначение (`accepted_at`) до перевода заказа в
`out_for_delivery` (DEC-52, DEC-83). До принятия курьер может
отказаться: назначение получает статус `declined`, заказ сохраняет
текущий статус, отказавшийся курьер исключается из автоназначения на
этот заказ, администратор назначает другого; после принятия отказ
недоступен (DEC-92); после перехода заказа в `out_for_delivery` отказ
также запрещён, в том числе если назначение не было принято
(вмешательство администратора, DEC-91, DEC-151 п. 5). Неудачная
доставка в v1 не имеет отдельного статуса и решается администратором
вне системы (DEC-151 п. 1). Точка на общей границе зон относится к зоне с
меньшей стоимостью доставки, при равенстве --- с меньшим UUID (DEC-102).
Live-карта не требуется.

Персонал видит только необходимые данные (DEC-106): курьер --- данные
клиента для доставки только по своим активным назначениям; повар --- без
имени, телефона, адреса, общего комментария клиента (`customer_comment`)
и платёжных данных, но с пожеланиями к позициям (`special_instructions`,
DEC-112).

## Уведомления

-   Внутренние уведомления и Telegram в v1 --- только для клиентов
    (DEC-57, DEC-85): при каждом изменении статуса их заказа и при
    решении по запросу отмены.
-   Внутренние уведомления хранятся как `type` + `payload`; текст
    формирует frontend через i18next (DEC-55).
-   Telegram: привязка через одноразовый токен/deep link на 10 минут
    (DEC-87) или из Mini App по email и паролю (DEC-152); отвязка требует
    текущий пароль и недоступна аккаунту без email и пароля (DEC-152);
    бот работает через long polling (DEC-03); язык сообщения
    фиксируется в событии outbox при его создании (DEC-105); отправка
    через transactional outbox с повторами; ошибка Telegram не
    откатывает заказ (DEC-75).
-   Изменения статусов публикуют доменные события, к которым подключены
    уведомления (DEC-79).
-   Клиентские экраны заказов обновляются polling каждые 20 секунд
    (DEC-74); административная панель, кухня и курьерский интерфейс ---
    каждые 10 секунд (DEC-93).

## Dashboard

Метрики (DEC-90), даты группируются в `Asia/Bishkek`:

-   количество заказов --- созданные в периоде (`created_at`), кроме
    mock-заказов, отменённых по `payment_timeout`;
-   выручка --- сумма завершённых заказов (`completed_at` в периоде);
-   средний чек --- выручка / число завершённых заказов, 2 знака; 0 при
    отсутствии завершённых;
-   активные заказы --- текущее число заказов в статусах `confirmed`,
    `preparing`, `ready_for_pickup`, `out_for_delivery`, независимо от
    периода (DEC-111);
-   график --- по дням две линии: созданные заказы (по `created_at`) и
    выручка (по `completed_at`), разные принципы явно подписаны; период
    по умолчанию --- последние 7 дней (DEC-111, DEC-114);
-   популярные товары --- топ-10 по суммарному количеству в завершённых
    заказах за период (DEC-111).

Заказы, ожидающие mock-оплаты, входят в количество созданных;
исключаются только отменённые по `payment_timeout`. Период по
умолчанию для сводных метрик, графика и топ-10 --- последние 7 дней;
границы дней --- `Asia/Bishkek` (DEC-114).

## UI

Чистый premium стиль: белый/кремовый фон, оранжевые акценты, умеренные
анимации, mobile-first, desktop/tablet/mobile. Карты --- Leaflet +
OpenStreetMap (DEC-01). Подробности --- `UI_UX_GUIDELINES.md`.

## Критерии MVP

1.  Регистрация, вход, refresh и logout работают; сотрудник меняет
    временный пароль при первом входе.
2.  Каталог и переводы отображаются.
3.  Варианты/модификаторы (включая количество модификаторов) влияют на
    серверную цену.
4.  Корзина сохраняется на сервере.
5.  Checkout проверяет адрес, зону, минимум заказа, рабочие часы и
    доступность способа получения.
6.  Самовывоз работает без адреса.
7.  Повтор запроса не создаёт дубликат заказа.
8.  Администратор управляет заказами, каталогом, зонами и персоналом.
9.  Клиент запрашивает отмену; администратор рассматривает.
10. Курьер видит только свои назначения, принимает их до выезда или
    отказывается до принятия и до перехода заказа в `out_for_delivery`
    (DEC-151 п. 5).
11. Mock payment не списывает деньги; неоплаченный mock-заказ
    отменяется через 30 минут.
12. Telegram linking использует одноразовый токен; привязка из Mini App
    требует проверенный `init_data` и пароль аккаунта (DEC-152).
13. Изменение цены не проходит незаметно (`PRICE_CHANGED`).
