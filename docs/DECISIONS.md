## Приоритет

До тех пор, пока остальные документы в `docs/` не будут приведены в
соответствие, **этот файл имеет приоритет** над
`TECHNICAL_SPECIFICATION.md`, `DATABASE_SCHEMA.md`,
`API_SPECIFICATION.md`, `UI_UX_GUIDELINES.md` и `DEVELOPMENT_PLAN.md` в
пунктах, где они расходятся. Новые решения добавляются сюда с новым
номером; принятые решения не переписываются молча — изменение
оформляется новой записью со ссылкой на заменяемую.

Нумерация `DEC-NN` совпадает с нумерацией утверждённого списка решений.

## 1. Архитектура и инфраструктура

- **DEC-01. Карты.** Leaflet + OpenStreetMap вместо обязательной
  интеграции Google Maps. Клиент ставит точку на карте и дополнительно
  вводит адрес текстом. Для доставки координаты обязательны.
- **DEC-02. Разрешённые дополнительные зависимости:** `slowapi`,
  `Pillow`, Mailpit (Docker-сервис для перехвата email), `openapi-typescript`
  (dev), `leaflet` и библиотека рисования полигонов для Leaflet
  (конкретная библиотека выбирается при реализации редактора зон и
  указывается в отчёте этапа).
- **DEC-03. Telegram** в демонстрационной версии работает через
  long polling (отдельный процесс/сервис). Webhook в v1 не используется.
- **DEC-04. Docker Compose — два режима:**
  - `dev` — hot reload backend и frontend;
  - `demo` — production-сборка frontend, раздача через nginx, единый
    origin для frontend и `/api/v1`.
- **DEC-05. Git** инициализируется на Этапе 1 вместе с `.gitignore`
  (исключает `.env`, локальные БД, volumes, `node_modules`, кэши, build).

## 2. Товары и цены

- **DEC-06.** Каждый товар имеет минимум один `product_variant`. Для
  простых товаров создаётся вариант «Стандарт». Поле
  `products.base_price` удаляется. `cart_items.variant_id` и
  `order_items.variant_id` (на момент создания) обязательны. Цена «от» в
  каталоге вычисляется как минимальная цена доступного варианта.
- **DEC-07.** Модификаторы поддерживают количество (например, двойной
  сыр). API принимает `modifiers: [{"id": "uuid", "quantity": 1}]`.
- **DEC-08.** Все расчёты стоимости выполняются только на backend, в
  едином модуле расчёта цены (используется корзиной, quote и созданием
  заказа).
- **DEC-09.** `expected_total` в запросе создания заказа используется
  только для сравнения с актуальным расчётом и никогда не считается
  доверенным значением.
- **DEC-10.** При расхождении `expected_total` с актуальным расчётом
  сервер возвращает `409 PRICE_CHANGED` и актуальный расчёт (quote) в
  `error.details`/теле ошибки. Заказ при этом не создаётся.

## 3. Корзина и заказ

- **DEC-11.** Позиции корзины с одинаковыми товаром, вариантом, набором
  модификаторов (с количествами) и пожеланиями объединяются
  (увеличивается `quantity`).
- **DEC-12.** `PATCH /cart/items/{id}` изменяет только `quantity` и
  `special_instructions`. Для смены варианта/модификаторов позиция
  удаляется и добавляется заново. Если после изменения пожеланий позиция
  совпала с другой — они объединяются (DEC-11).
- **DEC-13.** Гостевой корзины нет. «В корзину» без авторизации —
  переход на вход с возвратом на страницу товара.
- **DEC-14.** Номер заказа: `OSH-` + номер из PostgreSQL sequence,
  дополненный нулями минимум до 6 цифр (`OSH-000123`). *Уточнено DEC-123:
  номер никогда не обрезается (`OSH-1000000`), генерация в БД.*
- **DEC-15.** Snapshot названий товаров, вариантов, групп модификаторов
  и модификаторов сохраняется на языке клиента в момент оформления.
  Язык оформления сохраняется в заказе (`orders.language_code`).
- **DEC-16.** Неизменяемый snapshot адреса и стоимости доставки хранится
  в `orders`. Таблица `deliveries` хранит только операционные данные
  (зона, комментарий для курьера, `delivered_at`), без дублирования
  адреса, координат и стоимости.

## 4. Минимальная сумма и рабочее время

- **DEC-17.** Доставка: используется `delivery_zones.min_order_amount`,
  если он больше 0; иначе `restaurant_settings.min_order_amount`.
- **DEC-18.** Самовывоз: используется `restaurant_settings.min_order_amount`.
- **DEC-19.** Минимальная сумма сравнивается с `subtotal` без стоимости
  доставки.
- **DEC-20.** Заказы вне рабочих часов не принимаются (проверка в quote
  и при создании заказа, по времени `Asia/Bishkek`).
- **DEC-21.** Поддерживаются ночные интервалы: если `closes_at <
  opens_at`, интервал переходит через полночь. Время после полуночи
  относится к интервалу предыдущего дня недели.
- **DEC-22.** `delivery_enabled` и `pickup_enabled` проверяются при
  quote и при создании заказа.

## 5. Роли и сотрудники

- **DEC-23.** Роли сочетаются. Сотрудник (cook/courier) может также
  иметь роль `customer`. Клиентские функции (корзина, адреса, свои
  заказы) доступны при наличии роли `customer`.
- **DEC-24.** Роль `customer` выдаётся при регистрации.
- **DEC-25.** Повар работает только через `/staff/kitchen/*` (доступ:
  `cook`, `admin`). Ответы повару не содержат телефон и адрес клиента.
  `GET /orders/{id}` доступен только владельцу.
- **DEC-26.** Удаление категории = деактивация (`is_active = false`).
- **DEC-27.** При выдаче роли `courier` автоматически создаётся
  `courier_profiles`.
- **DEC-28.** Администратор задаёт сотруднику временный пароль. При
  первом входе сотрудник обязан его сменить; до смены пароля доступны
  только смена пароля, `/auth/me` и logout.
- **DEC-29.** Нельзя снять роль `courier`, пока у сотрудника есть
  активные назначения (`409`).

## 6. Статусы заказов

- **DEC-30.** Доставка: `pending → confirmed → preparing →
  ready_for_pickup → out_for_delivery → completed`.
- **DEC-31.** Самовывоз: `pending → confirmed → preparing →
  ready_for_pickup → completed`.
- **DEC-32.** `rejected` разрешён только из `pending`.
- **DEC-33.** `cancelled` разрешён из любого незавершённого статуса до
  передачи заказа курьеру, т.е. из `pending`, `confirmed`, `preparing`,
  `ready_for_pickup`. Из `out_for_delivery`, `completed`, `rejected`,
  `cancelled` — запрещён.
- **DEC-34.** Подтверждает заказ (`pending → confirmed`) администратор.
- **DEC-35.** Повар выполняет `confirmed → preparing` и `preparing →
  ready_for_pickup`. Администратор также может выполнять эти переходы.
- **DEC-36.** Курьер (только по своему активному назначению) выполняет
  `ready_for_pickup → out_for_delivery` и `out_for_delivery →
  completed` для доставки. *Дополнено DEC-91: администратор может
  выполнить эти переходы как административное вмешательство.*
- **DEC-37.** Самовывоз завершает (`ready_for_pickup → completed`)
  администратор.

Каждый переход: проверка допустимости и роли в сервисном слое, в одной
транзакции обновление `orders.status` и запись `order_status_history`,
синхронизация `deliveries`/`courier_assignments`/`payments` по правилам
ниже.

## 7. Отмена заказов

- **DEC-38.** Клиент может создать запрос отмены в статусах `pending`,
  `confirmed`, `preparing`.
- **DEC-39.** После одобрения заказ переходит в `cancelled`.
- **DEC-40.** Успешный mock-платёж при этом получает статус `refunded`
  (только имитация, `is_simulated = true`).
- **DEC-41.** Активное назначение курьера получает статус `cancelled`.
- **DEC-42.** После отклонения запроса клиент может отправить новый
  запрос (одновременно — не более одного `pending`-запроса на заказ).

## 8. Оплата

- **DEC-43.** Наличный платёж (`cash`) создаётся в `pending` и становится
  `succeeded` в той же транзакции, где курьер переводит доставку в
  `completed` или администратор завершает самовывоз.
- **DEC-44.** `mock_card` создаёт платёж в `pending`.
- **DEC-45.** Заказ с `mock_card` может быть подтверждён администратором
  (`pending → confirmed`) только после успешной mock-оплаты.
- **DEC-46.** При неудачной mock-оплате клиент может повторить попытку
  (новая запись `payments`). Успешный платёж на заказ — не более одного.
- **DEC-47.** Реальных списаний нет; данные карты не запрашиваются и не
  сохраняются. `POST /payments/mock/confirm` принимает
  `{"order_id": "uuid", "outcome": "success" | "failure"}`.

## 9. Курьеры и зоны доставки

- **DEC-48.** Назначить курьера можно, начиная со статуса `confirmed` и
  до `out_for_delivery` (не включая).
- **DEC-49.** Автоматическое назначение запускается кнопкой
  администратора (`POST /admin/orders/{id}/auto-assign-courier`):
  выбирается доступный курьер с наименьшим числом активных назначений,
  меньшим его `max_active_orders`.
- **DEC-50.** Если свободных курьеров нет — `409 NO_COURIER_AVAILABLE`.
- **DEC-51.** Переназначение: текущее активное назначение →
  `cancelled`, создаётся новое (в одной транзакции).
- **DEC-52.** В `courier_assignments` добавляется `accepted_at`. Статус
  заказа при принятии не меняется.
- **DEC-53.** Активные зоны не могут пересекаться по площади. Касание
  только границами допускается (проверка: пересечение внутренностей,
  напр. `ST_Overlaps`/`ST_Relate` с маской внутренностей, а не
  `ST_Intersects`).

## 10. Языки и уведомления

- **DEC-54.** Snapshot заказа сохраняется на языке клиента (см. DEC-15).
- **DEC-55.** Уведомления хранятся как `type` + `payload JSONB`; текст
  на сайте формируется на frontend через i18next. Колонки
  `title`/`message` удаляются.
- **DEC-56.** Telegram-сообщения формируются на backend на языке
  пользователя. *Уточнено DEC-105: язык (`users.preferred_language`)
  фиксируется в событии outbox в момент его создания, а не в момент
  отправки.*
- **DEC-57.** В v1 Telegram-уведомления получают только клиенты: при
  каждом изменении статуса их заказа и при решении по запросу отмены.

## 11. База данных и безопасность

- **DEC-58.** Принимаются рекомендации аудита D1–D12 с учётом решений
  выше:
  - D1: CHECK для `modifier_groups`: `min_selections <= max_selections`
    (если max не NULL); `selection_type = 'single' → max_selections = 1`;
    `is_required ↔ min_selections >= 1`. *Строгая SQL-форма для `single` —
    DEC-128.*
  - D2: CHECK списка статусов для `order_status_history.old_status`/`new_status`.
  - D3: `courier_assignments.accepted_at` (DEC-52).
  - D4: partial UNIQUE `payments(order_id) WHERE status = 'succeeded'`.
  - D5: CHECK `delivery_zones`: `NOT is_active OR boundary IS NOT NULL`.
  - D6: индекс `products(category_id, is_available, sort_order) WHERE
    deleted_at IS NULL`.
  - D7: `idempotency_keys` обязательна, с колонкой `scope` (DEC-59).
  - D8: `order_item_modifiers.group_name` (DEC-60).
  - D9: формула суммы позиции (DEC-61).
  - D10: пользователи деактивируются (DEC-62); категории деактивируются
    (DEC-26).
  - D11: UUID и `updated_at` (DEC-63).
  - D12: `is_verified` не используется (DEC-64).
- **DEC-59.** `idempotency_keys` обязательна: `UNIQUE (user_id, scope,
  key)`, срок хранения 24 часа. Ключ записывается в той же транзакции,
  что и заказ. Повтор с тем же ключом и тем же `request_hash` возвращает
  исходный результат; с другим хешем — `409`; пока исходный запрос
  выполняется — `409 IDEMPOTENCY_IN_PROGRESS`. Ответы с ошибками не
  сохраняются.
- **DEC-60.** Snapshot `group_name` в `order_item_modifiers`.
- **DEC-61.** `order_items.total_price = (unit_price + Σ(modifier.unit_price
  × modifier.quantity)) × quantity`. `order_item_modifiers.total_price =
  unit_price × quantity` модификатора — на одну единицу позиции.
- **DEC-62.** Пользователи с историей заказов не удаляются физически, а
  деактивируются (`is_active = false`).
- **DEC-63.** UUID по умолчанию генерируется PostgreSQL
  (`gen_random_uuid()`); `updated_at` обновляется через SQLAlchemy
  (`onupdate`).
- **DEC-64.** `users.is_verified` в v1 не используется (подтверждения
  email нет).
- **DEC-65.** В `refresh_tokens` добавляются `family_id` и
  `replaced_by_id`. Повторное использование уже ротированного токена
  отзывает всю семью. *Уточнено DEC-110: без льготного окна; конкурентный
  refresh между вкладками предотвращается на frontend.*
- **DEC-66.** На каждом запросе backend проверяет актуальные роли и
  `is_active` по БД, а не только claims из JWT.
- **DEC-67.** Назначение курьера (ручное и автоматическое) выполняется с
  `SELECT … FOR UPDATE` на `courier_profiles` для соблюдения лимита.
- **DEC-68.** CSRF: проверка `Origin` и специального заголовка
  (например, `X-CSRF-Protection: 1`) для cookie-операций; refresh-cookie
  `HttpOnly`, `Secure` (в demo), `SameSite=Strict`,
  `Path=/api/v1/auth`. Единый origin: Vite proxy в dev, nginx в demo.
- **DEC-69.** Отдельная тестовая БД PostgreSQL + PostGIS (отдельный
  сервис/БД в Docker Compose).
- **DEC-70.** Изображения: Pillow, разрешены JPEG, PNG, WebP, до 5 МБ;
  проверка содержимого, имя файла генерируется сервером.
- **DEC-71.** Типы frontend генерируются из OpenAPI через
  `openapi-typescript`.

## 12. API и разработка

- **DEC-72.** Добавляются endpoints, найденные аудитом:
  - `PUT /admin/variants/{id}/modifier-prices` — переопределение цен
    модификаторов для варианта;
  - `GET /admin/categories`, `GET /admin/products`,
    `GET /admin/products/{id}`, `GET /admin/modifier-groups`,
    `GET /admin/modifiers` — с неактивными записями и всеми переводами;
  - `GET /restaurant` (public) — контакты, адрес, часы работы, флаги
    доставки/самовывоза;
  - `GET /telegram/link` — статус привязки;
  - `POST /admin/categories/{id}/image` — изображение категории;
  - `GET /admin/couriers` — курьеры с доступностью и числом активных
    назначений;
  - payload `POST /payments/mock/confirm` — DEC-47;
  - отдельный endpoint отметки наличной оплаты не нужен (DEC-43);
  - webhook Telegram в v1 не нужен (DEC-03);
  - `POST /auth/password/change` — следует из DEC-28.
- **DEC-73.** Ошибки FastAPI/Pydantic (включая `RequestValidationError`
  и `HTTPException`) приводятся к единому формату `{"error": {...}}`.
- **DEC-74.** Клиент получает обновления статуса заказа через RTK Query
  polling каждые 20 секунд (на страницах активного заказа).
- **DEC-75.** Telegram-уведомления отправляются через transactional
  outbox: запись в outbox в той же транзакции, что и изменение;
  отправка отдельным процессом с повторами. Ошибка Telegram не
  откатывает заказ.
- **DEC-76.** Демонстрационная зона доставки Оша создаётся seed-скриптом.
- **DEC-77.** Каркас админки (layout, навигация, guards по ролям)
  создаётся на этапе каталога.
- **DEC-78.** На этапе checkout создаётся `payments` в `pending`; полный
  жизненный цикл оплаты — на этапе платежей.
- **DEC-79.** Изменения статусов публикуют доменные события
  (внутрипроцессно, в той же транзакции), к которым позже подключаются
  уведомления и outbox.

## 14. Решения по вопросам Q-01…Q-06 (утверждено)

Окончательные формулировки:

- **DEC-80 (Q-06). Сроки токенов и rate limits.** Access token —
  15 минут. Refresh token — 30 дней, с ротацией и отзывом всей семьи при
  повторном использовании старого токена. Токен сброса пароля —
  30 минут, одноразовый. Login — не более 5 попыток в минуту с одного
  IP. Запрос сброса пароля — не более 3 раз в час на аккаунт/IP. Общий
  API — 120 запросов в минуту на пользователя. Публичные endpoints без
  авторизации — 60 запросов в минуту на IP. Все значения хранятся в
  конфигурации приложения и меняются без изменения бизнес-логики.
- **DEC-81 (Q-01). Модификаторы.** `max_selections` (и
  `min_selections`) считают количество **разных** выбранных
  модификаторов, а не сумму количеств. Добавляется
  `modifiers.max_quantity`; если не задан — 1. Одновременно проверяются
  минимальное и максимальное количество выборов и количество каждого
  модификатора.
- **DEC-82 (Q-03). Прямая отмена администратором.** Выполняет те же
  действия, что и одобренный запрос клиента: возврат mock-платежа
  (имитация), снятие назначения курьера, запись истории статусов и
  причины отмены. Операция идемпотентна: повторный запрос не приводит к
  повторному возврату или другим побочным эффектам.
- **DEC-83 (Q-04). Принятие заказа курьером.** Курьер обязан принять
  назначение до перехода заказа в `out_for_delivery`; при принятии
  заполняется `accepted_at`; без принятия переход запрещён (исключение
  — административное вмешательство, DEC-91).
- **DEC-84 (Q-02). Неоплаченный mock-заказ.** Если mock-платёж не
  завершён в течение 30 минут, заказ автоматически отменяется с причиной
  `payment_timeout`. До успешной оплаты заказ не попадает в рабочую
  очередь ресторана. Просроченные заказы обрабатывает фоновая задача.
- **DEC-85 (Q-05). Уведомления сотрудникам.** Внутренние уведомления
  сотрудникам в v1 не нужны. Уведомления (`type` + `payload`) и Telegram
  — только для клиентов. Рабочие экраны администратора, повара и курьера
  получают актуальные данные через API и polling.
- **DEC-86. Payload оформления заказа**: `delivery_type`; для доставки
  ровно одно из `address_id` или `address{...}` (+ `save_address`); для
  самовывоза адреса нет; `customer_name`, `customer_phone`, `comment`,
  `payment_method_code`, `expected_total`, необязательный `language`.
  Полная схема — `API_SPECIFICATION.md` §6.2.

Также подтверждены производные выводы: `users.must_change_password` и
`POST /auth/password/change` (DEC-28); `orders.language_code` (DEC-15);
отмена из `pending`, `confirmed`, `preparing`, `ready_for_pickup`
(DEC-33); пересечение зон по внутренним областям (DEC-53); Telegram
polling без webhook (DEC-03); автоматический `succeeded` для наличных
(DEC-43); таблица `telegram_outbox` (DEC-75).

## 15. Решения по вопросам Q-07…Q-15 и N-01…N-07 (утверждено 2026-11-05)

- **DEC-87 (Q-07). Токен привязки Telegram.** Срок жизни — 10 минут
  (конфигурация). Токен одноразовый: после успешной привязки повторно
  использовать его нельзя.
- **DEC-88 (Q-08, N-05). Первый администратор.**
  - Создаётся только CLI-командой `python -m app.cli create-admin`; в
    Docker — `docker compose exec backend python -m app.cli
    create-admin`.
  - Команда запрашивает имя и email (логин); пароль вводится дважды и
    не отображается в терминале; проверяется политикой DEC-96.
  - Работает, только если в системе ещё нет администратора.
  - Защищена от параллельного запуска (одна транзакция с
    `pg_advisory_xact_lock` и проверкой отсутствия администратора),
    поэтому невозможно создать двух «первых» администраторов.
  - `must_change_password = false`; хранится только Argon2id-хеш.
  - Пользователь создаётся только с ролью `admin` (уточнено DEC-113).
  - Стандартных учётных данных нет; пароль не хранится в исходном
    коде, env-файлах и логах.
- **DEC-89 (Q-09, N-06). Телефон.** Формат Кыргызстана: `+996` и 9 цифр.
  Backend нормализует и проверяет ввод: принимает `+996 700 12 34 56`,
  `996700123456`, `0700123456`, `700123456`; в БД хранится единый формат
  `+996700123456`. Frontend использует маску ввода, реализованную без
  дополнительной библиотеки; окончательная проверка — backend.
- **DEC-90 (Q-10, N-03). Метрики dashboard.**
  - Количество заказов — по `created_at` за выбранный период;
    исключаются только неоплаченные mock-заказы, отменённые по
    `payment_timeout`; остальные отменённые и отклонённые учитываются
    как созданные.
  - Выручка — сумма `total_amount` завершённых заказов по
    `completed_at`.
  - Средний чек — выручка / количество завершённых заказов (по
    `completed_at`), округление до двух знаков; при отсутствии
    завершённых — 0.
  - Группировка дат — `Asia/Bishkek`.
  - Остальные метрики — DEC-111; период по умолчанию — DEC-114.
- **DEC-91 (Q-11, N-01). Административное изменение курьерских
  статусов.**
  - Администратор может вручную выполнить переходы курьера
    (`ready_for_pickup → out_for_delivery`, `out_for_delivery →
    completed` для доставки) через `PATCH /admin/orders/{id}/status`.
  - Это административное вмешательство: обязательный комментарий;
    запись в `order_status_history` с `is_admin_override = true`,
    администратором (`changed_by`) и временем.
  - Ограничения state machine сохраняются; для перехода в
    `out_for_delivery` обязательно активное назначение курьера.
  - Фиктивный `accepted_at` не записывается, если курьер фактически не
    принимал назначение; достаточно признака в истории.
  - *Поведение `changed_by` при удалении пользователя — DEC-131.*
- **DEC-92 (Q-12, N-02). Отказ курьера.**
  - Endpoint `POST /courier/orders/{id}/decline` (необязательная
    причина).
  - Отказ разрешён только до принятия назначения; после принятия —
    `409 ASSIGNMENT_ALREADY_ACCEPTED`, дальнейшее переназначение
    выполняет администратор.
  - Назначение получает статус `declined`, заполняются `declined_at` и
    необязательное `decline_reason`.
  - Заказ сохраняет свой текущий статус.
  - Отказавшийся курьер исключается из повторного автоназначения на
    этот же заказ; администратор может назначить другого курьера.
- **DEC-93 (Q-13). Polling.** Административная панель, кухня и
  курьерский интерфейс — каждые 10 секунд; клиентские экраны заказов —
  каждые 20 секунд (DEC-74).
- **DEC-94 (Q-14, N-07). Библиотеки и инструменты.**
  - backend: `argon2-cffi`, `PyJWT`, `psycopg[binary]` v3,
    `GeoAlchemy2`, `httpx`, `python-multipart`, `pydantic-settings`,
    `pytest-asyncio`, `ruff` (вместе с DEC-02: `slowapi`, `Pillow`);
  - frontend: `leaflet`, `react-leaflet`, `@geoman-io/leaflet-geoman-free`
    (бесплатная версия), ESLint, Prettier (вместе с DEC-02:
    `openapi-typescript`);
  - базовые библиотеки Fixed stack сохраняются;
  - совместимые версии фиксируются в lock-файлах;
  - проверка геометрии и пересечения зон — на backend через PostGIS,
    данным frontend не доверяем.
- **DEC-95 (Q-15). SlowAPI.** В v1 API запускается одним процессом и
  одним Uvicorn worker; счётчики SlowAPI хранятся в памяти. При переходе
  к нескольким процессам или экземплярам API — Redis-backed rate
  limiter (отдельное согласование).
- **DEC-96 (N-04). Политика паролей.** 8–128 символов, минимум одна
  буква и одна цифра. Одна общая политика для регистрации, смены, сброса
  пароля и CLI-команды. Хеширование — Argon2id.

## 16. Производные детали P-01…P-14 (утверждено 2026-11-05)

- **DEC-97 (P-01). Ожидание оплаты.** Поле `orders.payment_due_at`:
  `created_at + 30 мин` для `mock_card`, NULL после успешной оплаты и для
  `cash`. Заказ `pending` с непустым `payment_due_at` не попадает в
  рабочую очередь; администратор видит такие заказы только с фильтром
  `awaiting_payment=true`, без действий.
- **DEC-98 (P-02). Причина отмены.** `orders.cancellation_reason_code`
  (`customer_request`, `admin_decision`, `payment_timeout`) и
  `orders.cancelled_at`; текст причины — в `order_status_history.comment`.
- **DEC-99 (P-03). Платежи.** Статус платежа `cancelled` (для `pending`
  платежей отменённых/отклонённых заказов, включая `cash`), поле
  `refunded_at`. Не более одной попытки `pending` на заказ; неудачная
  mock-попытка → `failed`, и сразу создаётся новая `pending`.
- **DEC-100 (P-04). Отклонение заказа** (`rejected`) применяет к
  платежам те же правила, что и отмена (успешный mock → `refunded`,
  `pending` → `cancelled`).
- **DEC-101 (P-05). Отмена через API администратора.** Прямая отмена и
  отклонение — через `PATCH /admin/orders/{id}/status` с обязательным
  `comment`. При прямой отмене `pending`-запрос клиента помечается
  `approved`; если заказ перешёл в статус, где отмена невозможна,
  `pending`-запрос автоматически отклоняется.
- **DEC-102 (P-06). Точка на общей границе зон.** Выбирается зона с
  меньшим `delivery_fee`; при равной стоимости — зона с меньшим UUID
  (`id`), чтобы результат всегда был одинаковым.
- **DEC-103 (P-07). Ошибки API.** Единый формат и каталог кодов
  (`API_SPECIFICATION.md` §1.1). Дополнения: `TELEGRAM_DISABLED` (409),
  `CSRF_FAILED` (403). `/auth/login` возвращает одинаковый
  `INVALID_CREDENTIALS` при неверном пароле, несуществующем email и
  неактивном аккаунте (отдельного кода для отключённого аккаунта нет;
  запросы деактивированного пользователя получают `401 UNAUTHORIZED`).
  Для неизвестных ошибок подробности сохраняются только в логах, клиенту
  — `INTERNAL_ERROR`. *Дополнено DEC-115.*
- **DEC-104 (P-08). Worker.** Один отдельный worker на `asyncio`, без
  Celery, APScheduler и брокеров; один экземпляр в v1; использует общие
  сервисы приложения; каждая задача — в отдельной транзакции; graceful
  shutdown; ошибки обрабатываются без остановки всего worker. Задачи и
  интервалы — `DATABASE_SCHEMA.md` §14.5 (значения в конфигурации).
- **DEC-105 (P-09). Telegram.** Polling; одноразовая привязка (DEC-87);
  в БД хранится только SHA-256 хеш токена; повторные отправки (до 5
  попыток, экспоненциальная задержка до 1 часа, обработка 429/403); чат
  другого аккаунта не привязывается; язык уведомления сохраняется в
  событии outbox в момент его создания, и последующее изменение
  настроек пользователя не меняет язык отложенной отправки; при не
  настроенном боте — `409 TELEGRAM_DISABLED`.
- **DEC-106 (P-10). Данные персонала.** Курьер видит только свои
  активные назначения и необходимые для доставки данные клиента (адрес
  из snapshot, имя, телефон, комментарии, состав, сумму к получению);
  после переназначения или отмены теряет доступ к подробностям прежнего
  заказа; в истории — без адреса и контактов. Повар работает только
  через `/staff/kitchen/*` и не видит имя, телефон, адрес, комментарии
  клиента к заказу (`customer_comment`) и платёжные данные;
  `special_instructions` позиций повару видны (подтверждено DEC-112).
- **DEC-107 (P-11). Рабочие часы.** Ровно один интервал работы на
  каждый день недели; ночной интервал (`closes_at < opens_at`)
  относится к дню открытия; `Asia/Bishkek`; круглосуточный режим и
  несколько интервалов в день в v1 не поддерживаются; `PUT
  /admin/working-hours` принимает полный набор из 7 дней.
- **DEC-108 (P-12). Сброс пароля.** Одинаковый ответ `202` для
  существующего и несуществующего email (и при превышении лимита);
  искусственная фиксированная задержка не добавляется; одноразовый
  reset-токен на 30 минут; в БД только SHA-256 хеш; после успешного
  сброса отзываются все семьи refresh-токенов; токены и ссылки не
  записываются в логи.
- **DEC-109 (P-13). Idempotency.** Обязательный `Idempotency-Key` для
  `POST /orders`; SHA-256 хеш канонического тела; срок хранения 24 часа;
  повтор с тем же ключом и телом возвращает сохранённый результат;
  другое тело — `IDEMPOTENCY_KEY_CONFLICT`; ошибки не сохраняются как
  результат; параллельная обработка защищается уникальным индексом
  PostgreSQL с `lock_timeout` (по таймауту — `IDEMPOTENCY_IN_PROGRESS`).
  Алгоритм — `DATABASE_SCHEMA.md` §14.2.
- **DEC-110 (P-14). Хранение сессии.** Access-токен — только в памяти
  Redux; refresh-токен — в HttpOnly Secure cookie; mutex внутри вкладки;
  координация между вкладками через `navigator.locks`; после получения
  блокировки вкладка выполняет refresh с актуальной cookie. Backend
  сохраняет строгую политику: повторное предъявление старого
  refresh-токена отзывает всю семью. **Льготное окно
  (`REFRESH_REUSE_GRACE_SECONDS`) отклонено** и не вводится.

## 17. Решения по Q-16 и уточнениям ред. 4 (утверждено 2026-11-05)

- **DEC-111 (Q-16). Остальные метрики dashboard** (дополняют DEC-90).
  1. **Активные заказы** — текущее количество заказов в статусах
     `confirmed`, `preparing`, `ready_for_pickup`, `out_for_delivery`;
     текущий показатель, не зависит от выбранного периода статистики.
  2. **График** — по дням периода две линии: количество созданных
     заказов по `created_at` (по правилу DEC-90) и выручка по
     `completed_at`. В интерфейсе явно обозначается, что линии
     считаются по разным принципам. Дни без данных показываются как 0.
  3. **Популярные товары** — топ-10 товаров по суммарному `quantity` в
     заказах `completed` с `completed_at` в выбранном периоде;
     группировка по `product_id`, название — из snapshot последнего
     такого заказа.
  4. **Заказы, ожидающие mock-оплаты**, учитываются в количестве
     созданных заказов согласно DEC-90; исключаются только заказы,
     отменённые по `payment_timeout`.
  5. **Период графика по умолчанию** — последние 7 дней (текущий день
     и 6 предыдущих). Все даты и границы дней рассчитываются в
     `Asia/Bishkek`.
- **DEC-112. Пожелания к позициям на кухне** (уточняет DEC-106). Повар
  видит `special_instructions` отдельных позиций заказа, так как они
  необходимы для приготовления. Общий `customer_comment` повару не
  показывается.
- **DEC-113. Роли первого администратора** (уточняет DEC-88).
  CLI-команда `create-admin` создаёт пользователя только с ролью
  `admin`; роль `customer` автоматически не добавляется и при
  необходимости назначается отдельно.
- **DEC-114. Период dashboard по умолчанию** (дополняет DEC-90 и
  DEC-111). Для сводных метрик, графика и топ-10 товаров период по
  умолчанию — последние 7 дней (текущий день и 6 предыдущих). Правила
  внутри периода:
  - количество созданных заказов — по `created_at` за выбранный период;
  - выручка (и средний чек) — по `completed_at` за выбранный период;
  - топ-10 товаров — по количеству в завершённых заказах за выбранный
    период;
  - активные заказы — текущее количество, независимо от выбранного
    периода;
  - все даты и границы дней — в `Asia/Bishkek`;
  - `date_from` и `date_to` включительны: `date_to` охватывает весь
    календарный день в `Asia/Bishkek`; внутренне используется
    полуоткрытый интервал `[начало date_from, начало дня после
    date_to)`, чтобы не терять записи последнего дня.
- **DEC-115. Дополнительные коды ошибок** (дополняет DEC-103; утверждено
  2026-11-07):
  - `SERVICE_UNAVAILABLE` — HTTP 503, база данных недоступна при
    healthcheck;
  - `METHOD_NOT_ALLOWED` — HTTP 405, неподдерживаемый HTTP-метод;
  - `HTTP_ERROR` — резервный код только для HTTP-ошибок, для которых в
    каталоге нет отдельного кода. Он не заменяет существующие коды
    (`NOT_FOUND`, `VALIDATION_ERROR`, `RATE_LIMITED`, `UNAUTHORIZED`,
    `FORBIDDEN` и др.).
  - Необработанные внутренние ошибки сервера, а также HTTP 5xx без
    отдельного кода в каталоге, всегда возвращают `INTERNAL_ERROR`;
    `HTTP_ERROR` для них не используется. Явные коды 5xx из каталога
    (например, `SERVICE_UNAVAILABLE`) сохраняются.

## 19. Решения по плану Stage 2 (утверждено 2026-11-07)

Решения документируют реализацию Stage 2; разрешения на саму
реализацию они не дают.

- **DEC-116 (S2-1). Миграции Stage 2** — 7 отдельных ревизий Alembic в
  порядке зависимостей внешних ключей:
  - `0002` — users, roles, user_roles, courier_profiles, addresses,
    refresh_tokens, password_reset_tokens;
  - `0003` — restaurant_settings, restaurant_working_hours,
    payment_methods, delivery_zones;
  - `0004` — каталог (13 таблиц, включая переводы,
    product_modifier_groups, variant_modifier_prices);
  - `0005` — carts, cart_items, cart_item_modifiers;
  - `0006` — orders, `order_number_seq` и функция номера заказа
    (DEC-123), order_items, order_item_modifiers, order_status_history,
    cancellation_requests, idempotency_keys;
  - `0007` — payments, deliveries, courier_assignments;
  - `0008` — notifications, telegram_links, telegram_link_tokens,
    telegram_outbox.

  Каждая ревизия имеет рабочий `downgrade`. Все миграции и
  destructive-проверки (`downgrade`) выполняются только на изолированной
  `db-test`; перед тестами явно проверяются имя и адрес тестовой БД.
  Основная БД мигрируется только вперёд (`upgrade`), `downgrade` на ней
  не выполняется.
- **DEC-117 (S2-2). Seed** — отдельная CLI-команда
  `python -m app.seeds <режим>`, а не data-миграции:
  - `base` — обязательные системные данные: роли `customer`, `admin`,
    `cook`, `courier`; способы оплаты `cash`, `mock_card`; строка
    `restaurant_settings` с `id = 1`; рабочие часы на 7 дней;
  - `demo` — демонстрационные данные: зона доставки и каталог
    (DEC-118…DEC-120);
  - оба режима идемпотентны: повторный запуск не создаёт дубликатов;
  - seed **не создаёт пользователей** (первый администратор — только
    CLI `create-admin`, DEC-88, DEC-113).
- **DEC-118 (S2-3). Демо-данные ресторана:**
  - название — `Demo Restaurant — Osh`;
  - глобальная минимальная сумма заказа — `300.00` KGS;
  - только явно демонстрационные контакты, не реальные. Предложенные
    значения *(конкретизация, требует подтверждения)*: телефон
    `+996000000000`, адрес с пометкой «демонстрационный адрес, г. Ош».
  *Контакты подтверждены DEC-125.*
- **DEC-119 (S2-4). Демо-зона и рабочие часы:**
  - одна демонстрационная зона доставки Оша; в `name` и `description`
    явно указано, что это демонстрационная зона, а не утверждённая
    рестораном зона обслуживания;
  - минимальная сумма заказа для зоны — `500.00` KGS;
  - стоимость доставки — `100.00` KGS *(значение из рекомендации S2-4; в
    ответе пользователя отдельно не названо — требует подтверждения)*;
  - рабочие часы — ежедневно `10:00–23:00` (`Asia/Bishkek`).
  *Стоимость доставки и остальные параметры подтверждены DEC-124.*
- **DEC-120 (S2-5). Демо-каталог:**
  - около 20 товаров, 2–3 на каждую из 8 категорий;
  - у каждого товара минимум один вариант (DEC-06), модификаторы с
    `max_quantity`;
  - без изображений;
  - переводы RU/KY/UZ создаются сразу; качество переводов проверяется
    отдельно.
- **DEC-121 (S2-6). Загрузка связей SQLAlchemy** — `lazy="raise"` для
  отношений; нужные связи загружаются явно через `selectinload` /
  `joinedload`. Неявная ленивая подгрузка в async-коде запрещена.
- **DEC-122 (S2-7). Валидность геометрии зоны** — CHECK
  `boundary IS NULL OR ST_IsValid(boundary)` в `delivery_zones`, в
  дополнение к проверке сервисом. NULL допустим (зона ещё не настроена;
  активная зона без границы запрещена отдельным CHECK, DEC-58).
- **DEC-123 (S2-8). Генерация номера заказа в БД** (уточняет формулу
  DEC-14):
  - номер формируется на уровне БД: sequence `order_number_seq` и
    `server_default` колонки `orders.order_number`;
  - формат — `OSH-` + номер, дополненный нулями минимум до 6 цифр и
    **никогда не обрезаемый**: `OSH-000001`, `OSH-999999`, `OSH-1000000`;
  - формула `lpad(n::text, 6, '0')` запрещена: PostgreSQL обрезает
    более длинную строку (`1000000` → `100000`), что даёт повторный
    номер и нарушение UNIQUE (проверено на PostgreSQL 16.15);
  - используется `lpad(n::text, greatest(6, length(n::text)), '0')`;
    чтобы `nextval` вызывался ровно один раз, выражение оформлено как
    SQL-функция (например, `next_order_number()`), которую вызывает
    `server_default`; функция создаётся в ревизии `0006` и удаляется в
    её `downgrade`;
  - номера не обязаны быть непрерывными: значения sequence, взятые
    откатившимися транзакциями, пропускаются;
  - обязательный тест на `db-test`: перевод sequence к 999999 и создание
    двух заказов → `OSH-999999` и `OSH-1000000`.
- **DEC-124. Подтверждение демо-параметров доставки** (подтверждает
  DEC-119; утверждено 2026-11-07):
  - стоимость доставки — `100.00` KGS;
  - минимальная сумма заказа для доставки — `500.00` KGS;
  - рабочее время — ежедневно `10:00–23:00` (`Asia/Bishkek`);
  - демо-зона находится в Оше и обозначена как демонстрационная, а не
    как утверждённая рестораном зона обслуживания (DEC-119).
- **DEC-125. Подтверждение демонстрационных контактов** (подтверждает
  DEC-118; утверждено 2026-11-07):
  - телефон — `+996000000000`;
  - адрес — `Демонстрационный адрес, г. Ош`;
  - это **фиктивные демонстрационные данные**: в seed, интерфейсе и
    документации они явно обозначаются как демонстрационные и не
    представляются как реальные контакты ресторана.
- **DEC-126 (Q-17, S2-9). Типы уведомлений — CHECK в БД** (вариант A;
  утверждено 2026-11-07; дополняет DEC-55, DEC-57, DEC-105):
  - CHECK constraint на `notifications.type` и
    `telegram_outbox.event_type`;
  - разрешённые значения v1: `order_status_changed`,
    `cancellation_request_approved`, `cancellation_request_rejected`;
  - в Python — один `StrEnum` с теми же значениями; он же служит
    источником списка для CHECK в миграции;

- **DEC-128. Строгий CHECK для `single`-групп модификаторов**
  (уточняет SQL-выражение D1 из DEC-58; утверждено 2026-11-07):
  - буквальное выражение `selection_type <> 'single' OR max_selections =
    1` пропускает строку `single` с `max_selections IS NULL`, потому что
    в CHECK результат NULL считается успехом; это противоречит смыслу
    D1 («`single` → `max_selections = 1`»);
  - используется строгое выражение
    `selection_type <> 'single' OR max_selections IS NOT DISTINCT FROM 1`:
    группа `single` обязана иметь `max_selections = 1`, NULL отклоняется;
  - для `multiple` `max_selections` по-прежнему может быть NULL
    («без ограничения»); остальные CHECK D1 не меняются.

- **DEC-136. Seed CLI: идемпотентность, демо-каталог и защиты**
  (уточняет DEC-117…DEC-120, DEC-124, DEC-125; утверждено 2026-11-08):
  - **Идемпотентность — только добавление.** Seed создаёт отсутствующие
    записи и никогда не изменяет и не удаляет существующие (изменения
    администратора сохраняются; удалённая демо-запись при повторном
    запуске создаётся снова). Повторный запуск не создаёт дубликатов.
    Записи с естественным уникальным ключом (`roles.name`,
    `payment_methods.code`, `restaurant_settings.id`,
    `restaurant_working_hours.weekday`, `categories.slug`,
    `products.slug`, `product_variants.sku`, переводы по
    `(…_id, language_code)`, составные PK связей) вставляются через
    `INSERT … ON CONFLICT DO NOTHING`. Всем записям режима `demo`

    нет естественного ключа) назначается детерминированный UUID —

    Схема БД не меняется.

    выполняются в одной транзакции под `pg_advisory_xact_lock`: при
    ошибке не остаётся частично созданных данных; параллельный запуск
    ждёт завершения первого и не создаёт дубликатов.

    - ревизия БД равна head Alembic;
    - `demo` требует выполненного `base`: строка `restaurant_settings`

      площади с существующей активной зоной (`ST_Relate(a, b,

- **DEC-137. Seed: принадлежность demo-записей и конфликты
  естественных ключей** (дополняет DEC-136; утверждено 2026-11-08):
  - **Принадлежность.** Для demo-записей, которым seed назначает
    детерминированный UUIDv5, принадлежность seed определяется только
    совпадением `id` с ожидаемым UUIDv5. Естественный ключ (`slug`,
    `sku` или другой уникальный ключ) сам по себе принадлежность не
    подтверждает. Для дочерних записей, существование которых
    определяется составным или естественным ключом, применяются правила
    идентификации из пункта «Как определяется существование дочерней
    записи».
  - **Родительские и дочерние записи.** Родительские demo-записи:
    `delivery_zones`, `categories`, `products`, `modifier_groups`,
    `modifiers`. Дочерние: переводы, `product_variants`,
    `product_modifier_groups`, `variant_modifier_prices`.
  - **Существующие записи.** Запись с ожидаемым UUIDv5 пропускается без
    сравнения и изменения её данных; изменения администратора
    сохраняются.
  - **Восстановление.** Отсутствующая demo-запись, в том числе
    родительская и ранее существовавшая, при повторном запуске
    создаётся снова (DEC-136).
  - **Дочерние записи.** Отсутствующие дочерние записи создаются только
    для родителей с ожидаемыми UUIDv5 (существующих или созданных этим
    же запуском) и после них. Существующая дочерняя запись не
    перезаписывается и не удаляется.
  - **Как определяется существование дочерней записи.**
    `product_variants`: по UUIDv5. Перевод: по паре «идентификатор
    родителя + `language_code`», а именно `category_translations` по
    (`category_id`, `language_code`), `product_translations` по
    (`product_id`, `language_code`), `product_variant_translations` по
    (`variant_id`, `language_code`), `modifier_group_translations` по
    (`group_id`, `language_code`), `modifier_translations` по
    (`modifier_id`, `language_code`). Связь `product_modifier_groups`:
    по составному PK (`product_id`, `group_id`). Цена
    `variant_modifier_prices`: по составному PK (`variant_id`,
    `modifier_id`).
  - **Конфликт естественного ключа.** Проверка конфликта применяется к
    уникальным естественным ключам demo-записей, которым seed назначает
    UUIDv5: `categories.slug`, `products.slug`, `product_variants.sku`.
    Если такой ключ создаваемой demo-записи занят записью с другим
    `id`, режим завершается понятной ошибкой со списком всех
    конфликтов, кодом выхода 1 и полным rollback. Переводы,
    определяемые по паре из идентификатора родителя и `language_code`,
    а также связи `product_modifier_groups` и цены
    `variant_modifier_prices`, определяемые по составному PK,
    конфликтом естественного ключа не считаются: существующая такая
    запись пропускается без изменения (пункт «Как определяется
    существование дочерней записи»).
  - **Запрещённые действия при конфликте.** Запрещено присоединять
    демо-товары к чужим категориям, присоединять демо-варианты к чужим
    товарам, перезаписывать или удалять конфликтующие записи и
    продолжать создание дочерних записей после обнаружения конфликта.
  - **Порядок проверки.** Все конфликты проверяются до первой вставки.
    Записи с естественным ключом вставляются с
    `ON CONFLICT (id) DO NOTHING`, поэтому конфликт, возникший после
    проверки, тоже приводит к ошибке и полному rollback.
  - **Режим `base`.** Роли, способы оплаты, `restaurant_settings` и
    рабочие часы являются системными записями без UUIDv5: существующие
    пропускаются по естественному ключу, отсутствующие создаются
    (DEC-136).
  - **Ревизия БД.** Seed выполняется, только если в миграциях ровно
    один head, в `alembic_version` ровно одна строка и она равна head;
    иначе выводится ошибка, код выхода 1, изменений нет.
  - **Smoke-тест CLI** (только `db-test`):
    - проверяет изоляцию `db-test` и точное имя тестовой БД;
    - до запуска проверяет отсутствие записей с ключами seed и
      конфликтующих записей; при их наличии тест падает, ничего не
      удаляя;
    - до запуска снимает множества первичных ключей всех затронутых
      таблиц: для таблиц с PK `id` фиксируются множества `id`, для
      таблиц с составным PK `product_modifier_groups` (`product_id`,
      `group_id`) и `variant_modifier_prices` (`variant_id`,
      `modifier_id`) фиксируются множества полных составных ключей;
    - записи, созданные именно этим запуском, определяются как разница
      множеств первичных ключей после и до запуска;
    - очистка удаляет только эти записи по точным первичным ключам,
      явно, от дочерних к родительским, одной транзакцией, со сверкой
      числа удалённых строк;
    - после очистки проверяет, что множества первичных ключей всех
      затронутых таблиц совпадают с исходным снимком;
    - при любой ошибке очистки откатывает её и сообщает об ошибке, не
      пытаясь удалять дополнительные записи.
- **DEC-138. Seed: детерминированные UUIDv5 и цели ON CONFLICT**
  (дополняет DEC-136 и DEC-137; утверждено 2026-11-08):
  - **Namespace.** Все UUIDv5 seed вычисляются как
    `uuid5(NAMESPACE, code)` с одним постоянным значением
    `NAMESPACE = "9001f190-2113-481c-a977-fe2b1f0212a0"`. Значение
    задаётся строковой константой в коде, один раз преобразуется в
    `uuid.UUID` и затем передаётся в `uuid5()`. Оно не генерируется
    при запуске и не меняется: при его изменении seed перестаёт
    распознавать свои записи. Значение не является секретом.
  - **Переменные кодов.** Значения переменных состоят только из
    строчных латинских букв, цифр и дефиса; точка в них не допускается
    и используется только как разделитель компонентов в итоговой
    строке `code`. Коды, назначенные записям, не меняются:
    - `zone_code` — код зоны, для демо-зоны `osh`;
    - `category_slug` — `slug` категории, например `pizza`;
    - `product_code` — код товара, например `pizza-margherita`;
      `slug` товара равен `"demo-" + product_code`, например
      `demo-pizza-margherita`;
    - `variant_code` — код варианта внутри товара, например `30`;
    - `group_code` — код группы модификаторов, например
      `pizza-dough`;
    - `modifier_code` — код модификатора внутри группы, например
      `cheese`.
  - **Формулы кодов.**
    - зона: `code = "demo.zone." + zone_code`, пример
      `demo.zone.osh`;
    - категория: `code = "demo.category." + category_slug`, пример
      `demo.category.pizza`;
    - товар: `code = "demo.product." + product_code`, пример
      `demo.product.pizza-margherita`;
    - вариант: `code = "demo.variant." + product_code + "." +
      variant_code`, пример `demo.variant.pizza-margherita.30`;
    - группа модификаторов: `code = "demo.group." + group_code`,
      пример `demo.group.pizza-dough`;
    - модификатор: `code = "demo.modifier." + group_code + "." +
      modifier_code`, пример `demo.modifier.pizza-extras.cheese`;
    - перевод: `code = "demo.translation." + parent_type + "." +
      parent_code + "." + language_code`, пример
      `demo.translation.modifier.pizza-extras.cheese.ky`.
  - **Код родителя перевода.** `parent_type` принимает одно из пяти
    значений: `category`, `product`, `variant`, `group`, `modifier`.
    `parent_code` формируется так:
    - для `category` — `category_slug`, пример `pizza`;
    - для `product` — `product_code`, пример `pizza-margherita`;
    - для `variant` — `product_code + "." + variant_code`, пример
      `pizza-margherita.30`;
    - для `group` — `group_code`, пример `pizza-dough`;
    - для `modifier` — `group_code + "." + modifier_code`, пример
      `pizza-extras.cheese`.
    `language_code` принимает значения `ru`, `ky`, `uz`. Примеры
    кодов переводов:
    - `demo.translation.category.pizza.ru`;
    - `demo.translation.product.pizza-margherita.ky`;
    - `demo.translation.variant.pizza-margherita.30.uz`;
    - `demo.translation.group.pizza-dough.ru`;
    - `demo.translation.modifier.pizza-extras.cheese.ky`.
  - **UUID переводов.** Каждой новой demo-записи перевода назначается
    `id` по формуле перевода. Принадлежность и существование перевода
    по-прежнему определяются только парой из идентификатора родителя
    и `language_code` (DEC-137); `id` для этого не используется:
    1. если ожидаемая пара уже существует, перевод пропускается без
       изменения; `id` существующей строки не сравнивается с
       ожидаемым UUIDv5;
    2. если ожидаемой пары нет, но ожидаемый UUIDv5 занят строкой с
       другой парой, это конфликт: понятная ошибка, код выхода 1 и
       полный rollback; такие конфликты проверяются до первой вставки
       вместе с конфликтами `categories.slug`, `products.slug` и
       `product_variants.sku` и выводятся общим списком;
    3. если ожидаемая пара появилась после предварительной проверки,
       вставка пропускает её по цели ON CONFLICT этой пары;
    4. если ожидаемый UUIDv5 занят после предварительной проверки,
       нарушение PRIMARY KEY не подавляется и приводит к ошибке, коду
       выхода 1 и полному rollback.
  - **Цели ON CONFLICT.** Каждая вставка seed выполняется оператором
    INSERT с явной целью ON CONFLICT:
    - `roles`: `ON CONFLICT (name) DO NOTHING`;
    - `payment_methods`: `ON CONFLICT (code) DO NOTHING`;
    - `restaurant_settings`: `ON CONFLICT (id) DO NOTHING`;
    - `restaurant_working_hours`:
      `ON CONFLICT (weekday) DO NOTHING`;
    - `delivery_zones`: `ON CONFLICT (id) DO NOTHING`;
    - `categories`: `ON CONFLICT (id) DO NOTHING`;
    - `category_translations`:
      `ON CONFLICT (category_id, language_code) DO NOTHING`;
    - `products`: `ON CONFLICT (id) DO NOTHING`;
    - `product_translations`:
      `ON CONFLICT (product_id, language_code) DO NOTHING`;
    - `product_variants`: `ON CONFLICT (id) DO NOTHING`;
    - `product_variant_translations`:
      `ON CONFLICT (variant_id, language_code) DO NOTHING`;
    - `modifier_groups`: `ON CONFLICT (id) DO NOTHING`;
    - `modifier_group_translations`:
      `ON CONFLICT (group_id, language_code) DO NOTHING`;
    - `modifiers`: `ON CONFLICT (id) DO NOTHING`;
    - `modifier_translations`:
      `ON CONFLICT (modifier_id, language_code) DO NOTHING`;
    - `product_modifier_groups`:
      `ON CONFLICT (product_id, group_id) DO NOTHING`;
    - `variant_modifier_prices`:
      `ON CONFLICT (variant_id, modifier_id) DO NOTHING`.
    Каждая цель совпадает с PRIMARY KEY или UNIQUE-ограничением
    таблицы.
  - **Без общего ON CONFLICT.** `ON CONFLICT DO NOTHING` без цели в
    seed запрещён. Нарушение любого ограничения вне указанной цели
    (другого UNIQUE, PRIMARY KEY, FOREIGN KEY или CHECK) не
    подавляется и приводит к ошибке, коду выхода 1 и полному
    rollback. Тесты seed проверяют, что у каждой вставки задана явная
    цель.
  - DEC-137 не изменяется; DEC-138 дополняет DEC-136 и DEC-137 и не
    заменяет их.
- **DEC-139. Seed demo: пересечение зон, мягкое удаление и виды
  ошибок** (дополняет DEC-136, DEC-137 и DEC-138, не заменяя их;
  утверждено 2026-11-09):
  - **Проверка пересечения зон.** Расширяет условие предусловия
    DEC-136 о пересечении: проверка выполняется не только при первом
    создании демо-зоны, но и при каждом подходящем запуске `demo`,
    чтобы обнаруживать пересечения, появившиеся после её создания.
    Случаи определяются по строке `delivery_zones` с ожидаемым
    UUIDv5 демо-зоны:
    - демо-зоны нет — проверка выполняется, так как зона будет
      создана активной;
    - демо-зона существует и активна — проверка выполняется;
    - демо-зона существует и неактивна — проверка пропускается: по
      DEC-53 запрещено пересечение только активных зон.
  - **Как выполняется проверка.**
    - Собственная демо-зона исключается из поиска по ожидаемому
      UUIDv5; проверяются все остальные активные зоны с границей.
    - Для сравнения используется только утверждённая геометрия
      `DEMO_ZONE` (`DEMO_ZONE.boundary_wkt`, SRID 4326). Колонка
      `boundary` существующей демо-зоны из БД для этой проверки не
      читается.
    - Пересечением считается пересечение внутренних областей:
      `ST_Relate(boundary, ST_GeomFromText('<WKT DEMO_ZONE>', 4326),
      'T********')` (DEC-53). Касание границ и неактивные зоны
      ошибкой не являются.
    - Из существующей демо-зоны читается только `is_active`, и
      только для выбора случая из предыдущего пункта; это не
      сравнение и не изменение её данных в смысле DEC-137.
  - **Существующие демо-записи не изменяются.** Seed не меняет
    `is_active`, `is_available`, `deleted_at` и другие данные
    существующих демо-записей (DEC-136, DEC-137); в том числе не
    активирует неактивную демо-зону.
  - **Мягкое удаление.** Запись с ожидаемым UUIDv5 считается
    существующей независимо от `deleted_at` (среди demo-записей эта
    колонка есть только у `products`). Seed не очищает `deleted_at`;
    отсутствующие дочерние записи мягко удалённого демо-товара
    создаются по правилам DEC-137.
  - **Известное ограничение.** Advisory lock seed (DEC-136) не
    защищает от зон, созданных или изменённых в обход seed после его
    проверки; БД пересечение зон не запрещает.
  - **Будущий сервис зон.** Сервис создания и изменения зон обязан
    использовать тот же advisory lock key, что и seed: константу
    `SEED_ADVISORY_LOCK_KEY` из `app/seeds/common.py` (значение
    `0x5EED_0136`, то есть `1592590646`), через
    `pg_advisory_xact_lock`. Блокировка берётся до проверки
    пересечений (DEC-53) и удерживается в той же транзакции до
    завершения этой проверки и записи или изменения зоны; она
    снимается только при commit или rollback этой транзакции.
  - **Виды ошибок.** Режим `demo` различает три вида ошибок. Каждая
    выводится отдельным понятным сообщением, завершает режим с кодом
    выхода 1 и полным rollback и возникает до первой вставки.
    Проверки выполняются строго в этом порядке; при ошибке вида 1
    или 2 следующие проверки не выполняются:
    1. Не выполнен `base`: нет строки `restaurant_settings` с
       `id = 1`, какой-либо из 4 ролей или какого-либо из 2 способов
       оплаты (DEC-136). Сообщение перечисляет недостающее и
       предлагает сначала запустить `python -m app.seeds base`.
    2. Пересечение демо-зоны с другими активными зонами. Сообщение
       перечисляет `id` пересекающихся зон.
    3. Конфликты естественных ключей (`categories.slug`,
       `products.slug`, `product_variants.sku`, DEC-137) и UUID
       переводов (DEC-138) — одним общим списком с подробностями:
       таблица, код записи, ключ, найденный `id` или пара.
  - DEC-136, DEC-137 и DEC-138 не изменяются; DEC-139 дополняет их и
    не заменяет.
- **DEC-140. Auth backend: JWT, refresh, сессии, CSRF, пароли**
  (уточняет DEC-28, DEC-65, DEC-66, DEC-68, DEC-80, DEC-96, DEC-108,
  DEC-110; утверждено 2026-11-09):
  - **Access JWT.** Алгоритм HS256. Секрет — обязательная переменная
    окружения `JWT_SECRET_KEY` без значения по умолчанию, не короче 32
    символов; не выводится в логи и ответы. Claims: `sub` (id
    пользователя), `type` (`access`), `iat`, `exp`; срок — 15 минут
    (DEC-80). Роли и флаги в токен не помещаются: роли, `is_active` и
    `must_change_password` проверяются по БД на каждом запросе
    (DEC-66). При разборе разрешается только HS256 и только
    `type = access`; токен с другим алгоритмом, типом, подписью или
    истёкшим `exp` отклоняется с `401 UNAUTHORIZED`.
  - **Refresh-токен.** 32 случайных байта в кодировке Base64URL; в
    cookie хранится исходный токен, в `refresh_tokens.token_hash` —
    его SHA-256 в hex. Срок — 30 дней (DEC-80). Ротация: при каждом
    refresh создаётся новый токен той же семьи, старому выставляются
    `revoked_at` и `replaced_by_id` (DEC-65).
  - **Запрос `/auth/refresh`.** Требует проверку CSRF. Проверки
    выполняются строго в таком порядке; при отказе ответ
    `401 INVALID_REFRESH_TOKEN`:
    1. cookie нет или токен неизвестен — ничего не отзывается;
    2. владелец токена неактивен — отзываются все refresh-сессии
       пользователя независимо от состояния предъявленного токена;
    3. токен уже ротирован или отозван (`revoked_at` задан) —
       отзывается вся его семья (DEC-65, DEC-110);
    4. срок токена истёк, токен не ротирован и не отозван — ничего не
       отзывается.
    Льготного окна нет (DEC-110). Успешный refresh возвращает
    `access_token`, `token_type`, `expires_in` и новую refresh-cookie.
  - **Атомарность ротации.** Refresh выполняется в одной транзакции:
    после предварительного чтения `user_id` по хешу токена без
    блокировки блокируется строка пользователя
    (`SELECT is_active … FOR NO KEY UPDATE`), и значение `is_active`
    берётся только из этого блокирующего чтения; затем блокируется и
    перечитывается строка токена (`SELECT … FOR UPDATE`). Значения,
    прочитанные до получения блокировок, в том числе из загруженных
    ранее ORM-объектов, для проверок не используются. Старый токен
    помечается отозванным условием `revoked_at IS NULL` с проверкой,
    что изменена ровно одна строка; иначе транзакция откатывается и
    возвращается `401 INVALID_REFRESH_TOKEN`. Если два запроса
    одновременно предъявляют один токен, второй после ожидания видит
    его отозванным и обрабатывается как повторное предъявление:
    отзывается вся семья, включая токен, выданный первому запросу
    (DEC-65, DEC-110). Независимая вторая ветвь семьи создана быть не
    может.
  - **Фиксация результата до ответа.** Отказы refresh из четырёх
    пунктов части «Запрос `/auth/refresh`» (нет cookie или токен
    неизвестен; владелец неактивен; токен ротирован или отозван; срок
    истёк) не выбрасываются как исключения внутри транзакции: сервис
    возвращает результат, транзакция завершается штатно (COMMIT), и
    только после подтверждения успешного COMMIT отправляется
    `401 INVALID_REFRESH_TOKEN`. Так отзыв семьи или всех сессий не
    может быть отменён ROLLBACK при выходе из транзакционного
    контекста. Отказ при несовпадении числа изменённых строк (часть
    «Атомарность ротации») выдаётся после ROLLBACK; на этом пути токены
    не отзываются. Если приложение не получило подтверждение успешного
    COMMIT, оно не отправляет ответ, предполагающий успешное выполнение
    операции, не отправляет новую refresh-cookie и возвращает
    `500 INTERNAL_ERROR`. Если ошибка возникла во время COMMIT и
    результат фиксации неизвестен, фактическое состояние транзакции
    также считается неизвестным: она могла быть зафиксирована или
    отменена. Нельзя утверждать, что отзыв обязательно не произошёл.
    Те же правила действуют для logout и смены пароля: ответ `204` и
    очистка cookie — только после подтверждения успешного COMMIT; без
    подтверждения — `500 INTERNAL_ERROR`, cookie не очищается,
    результат отзыва считается неизвестным.
  - **Единый порядок блокировок.** Все операции, которые изменяют
    активность пользователя или состояние его refresh-сессий, берут
    блокировки в одном порядке: сначала строка `users`
    (`FOR NO KEY UPDATE`), затем строки `refresh_tokens`. Это
    относится к refresh, logout, смене пароля, сбросу пароля
    (DEC-108), деактивации пользователя и административному отзыву его
    refresh-сессий, а также к любым будущим операциям такого рода.
  - **Условие реализации: READ COMMITTED.** Операции из пункта о едином
    порядке блокировок выполняются на уровне изоляции READ COMMITTED,
    заданном явно в конфигурации подключения SQLAlchemy
    (`isolation_level`), а не только по умолчанию сервера PostgreSQL;
    тесты проверяют уровень внутри транзакции refresh. На этом уровне
    каждый оператор видит данные, зафиксированные до его начала, а
    блокирующее чтение после ожидания возвращает последнюю
    зафиксированную версию строки. Уровни REPEATABLE READ и
    SERIALIZABLE для этих операций не используются: при них повторное
    чтение заблокированной строки завершается ошибкой сериализации.
  - **Cookie.** Имя `refresh_token`; `HttpOnly`, `SameSite=Strict`,
    `Path=/api/v1/auth`, `Max-Age` равен сроку refresh-токена. Флаг
    `Secure` устанавливается при `APP_ENV=demo`; при `APP_ENV=dev` и
    `APP_ENV=test` он не устанавливается (DEC-68). Режим `production`
    не вводится; DEC-68 и DEC-110 не изменяются.
  - **Регистрация.** `POST /auth/register` создаёт пользователя с ролью
    `customer` (DEC-24) и сразу авторизует: ответ `201` с
    `access_token`, `token_type`, `expires_in` и refresh-cookie новой
    семьи. Занятый email — `409 EMAIL_ALREADY_EXISTS`.
  - **Вход.** Неверный пароль, неизвестный email и неактивный аккаунт
    дают одинаковый `401 INVALID_CREDENTIALS`. Для неизвестного email
    пароль проверяется против заранее вычисленного фиктивного
    Argon2id-хеша, чтобы время ответа не раскрывало существование
    аккаунта.
  - **Logout.** Только по refresh-cookie; access-токен не требуется;
    проверка CSRF обязательна. Если запись токена существует (в том
    числе с истёкшим сроком, ротированная или отозванная), отзывается
    вся её семья. Ответ всегда `204`, в том числе без cookie или с
    неизвестным токеном; cookie очищается. Access-токен после logout
    остаётся действительным до истечения срока, не более 15 минут; это
    принятое ограничение.
  - **Обязательная смена пароля.** Пока `must_change_password = TRUE`,
    из маршрутов, требующих авторизации, доступны только:
    - `/auth/me`;
    - `/auth/password/change`;
    - `/auth/logout`;
    - `/auth/refresh`.
    Остальные возвращают `403 PASSWORD_CHANGE_REQUIRED`.
    `/auth/refresh` выдаёт новую пару токенов, флаг при этом
    сохраняется; `/auth/me` возвращает его значение. Публичные маршруты
    без авторизации этим правилом не затрагиваются. Уточняет DEC-28: к
    его перечню добавлен `/auth/refresh`, чтобы сессия не обрывалась до
    смены пароля.
  - **Смена пароля.** Требует текущий пароль; новый пароль проверяется
    политикой DEC-96. При успехе сбрасывается `must_change_password` и
    отзываются все семьи refresh-токенов пользователя, включая текущую;
    cookie очищается; требуется повторный вход. Уже выданный
    access-токен остаётся действительным до истечения срока, не более
    15 минут; это принятое ограничение, как и для logout; списки отзыва
    и версии токенов не вводятся.
  - **CSRF.** Для `/auth/refresh` и `/auth/logout` заголовок `Origin`
    должен точно совпадать с одним из значений настройки
    `CSRF_TRUSTED_ORIGINS`, а заголовок `X-CSRF-Protection` —
    равняться `1`. Отсутствие или несовпадение любого из них —
    `403 CSRF_FAILED` (DEC-68).
  - **Argon2id.** Профиль RFC 9106 с 64 МиБ памяти (значения по
    умолчанию `argon2-cffi`). Параметры хеширования задаются в
    конфигурации, чтобы тесты могли использовать облегчённые значения;
    при успешном входе хеш со старыми параметрами пересчитывается.
  - **Rate limits** — по DEC-80 и DEC-95 без изменений.
  - **Письма сброса пароля.** Отправляются через стандартный `smtplib`
    в фоновой задаче FastAPI `BackgroundTasks` после ответа; параметры
    SMTP и адрес frontend — из конфигурации; токены и ссылки не пишутся
    в логи (DEC-108).
  - DEC-01–DEC-139 не изменяются; DEC-140 их уточняет и не заменяет.
- **DEC-141. Поля регистрации** (уточняет DEC-89, DEC-96, DEC-140;
  утверждено 2026-11-10). Тело `POST /auth/register`:
  - `email` — обязательно. Формат проверяется библиотекой
    `email-validator` без проверки домена через DNS. Пробелы по краям
    удаляются; для хранения и проверки уникальности адрес приводится к
    нижнему регистру; сравнение email всегда выполняется без учёта
    регистра. Длина после нормализации — не более 255 символов. Так же
    email нормализуется при входе, сбросе пароля,
    `POST /auth/credentials` (DEC-142) и создании сотрудника. Занятый
    email (без учёта регистра) — `409 EMAIL_ALREADY_EXISTS`.
  - `password` — обязательно, политика DEC-96. Буква — любая буква
    Unicode, цифра — любая десятичная цифра Unicode, длина считается в
    символах (code points). Пароль не обрезается и не изменяется.
  - `full_name` — обязательно. Пробелы по краям удаляются; после этого
    длина от 1 до 150 Unicode-символов (code points). Управляющие
    символы запрещены.
  - `phone` — необязательно; нормализация DEC-89, внутри номера
    допускаются только пробелы.
  - `preferred_language` — необязательно; `ru`, `ky` или `uz`, по
    умолчанию `ru`. Frontend передаёт текущий язык интерфейса.
  - Неизвестные поля (`role`, `is_active`, `user_id` и т. п.)
    отклоняются с `422 VALIDATION_ERROR`. Роль — всегда `customer`
    (DEC-24).
  - Нарушение правил полей — `422 VALIDATION_ERROR`. Ответ — по
    DEC-140. Frontend проверяет те же правила (Zod: `\p{L}`, `\p{Nd}`,
    длина по code points); окончательная проверка — на backend.
- **DEC-142. Telegram Mini App — основной клиентский канал заказа**
  (уточняет DEC-57, DEC-87, DEC-96, DEC-103, DEC-105, DEC-108,
  DEC-140; утверждено 2026-11-10):
  - **Назначение.** Mini App реализует полный клиентский сценарий: меню,
    корзина, оформление, mock-оплата, заказы, профиль. Используются тот

    доступен только роли `customer` (DEC-57). Оплата — только mock card;
    Telegram Payments не используются.
  - **Вход (K1-B).** `POST /auth/telegram/webapp {init_data}`, публичный
    endpoint:
    1. `init_data` проверяется на backend до использования любых
       содержащихся в нём данных. Ключ —
       `HMAC-SHA256(key="WebAppData", msg=<токен бота>)`; строка
       проверки — все поля, кроме `hash`, в виде `key=value`,
       отсортированные по ключу и разделённые `\n`; подпись
       сравнивается за постоянное время.
    2. Отклоняются: отсутствие `hash`, `auth_date` или `user`;
       повторяющиеся ключи; превышение допустимой длины;
       `auth_date` старше `TELEGRAM_WEBAPP_AUTH_MAX_AGE_SECONDS`
       (по умолчанию 3600) или в будущем сверх допустимого расхождения
       часов; `user.is_bot = true`.

       до 60 секунд (настраиваются); алгоритм подписи.*
    3. `initDataUnsafe` и любые данные Telegram, не прошедшие проверку,
       не используются для аутентификации.
    4. Пользователь ищется по `telegram_links.telegram_chat_id =
       user.id`. Активность и роли проверяются по БД: неактивный
       пользователь — `401 INVALID_TELEGRAM_AUTH`, пользователь без роли
       `customer` — `403 FORBIDDEN`.

       TELEGRAM_NOT_LINKED`, аккаунт при входе не создаётся.*

       refresh-cookie. После истечения access-токена Mini App повторяет
       обмен с `init_data`; по истечении срока `init_data` Mini App
       перезапускается.

       причины. Если бот не настроен — `409 TELEGRAM_DISABLED`. Лимит
       запросов — как у `/auth/login` (DEC-80).
       *Уточнено DEC-152 п. 4: отдельный счётчик, 5 запросов в минуту
       на IP.*

  - DEC-01–DEC-147 не изменяются.
- **DEC-149. Решения этапа 7 (платежи)** (утверждено 2026-11-12; снимает
  временное ограничение DEC-148 п. 1):
  1. **`mock_card` разрешён.** `POST /orders` принимает активный способ
     оплаты (`cash` или `mock_card`); неактивный или неизвестный —
     `422 VALIDATION_ERROR` (`payment_method_code`). Для `mock_card` в той
     же транзакции заказа создаётся попытка `payments`: `pending`,
     `is_simulated = true`, `amount = total_amount`, `currency = KGS`,
     `transaction_reference` = уникальный `MOCK-…` (создаётся вместе с
     попыткой, не банковский); `orders.payment_due_at = created_at +
     PAYMENT_TIMEOUT_MINUTES` (30). Сценарий `cash` не меняется
     (DEC-148): платёж остаётся `pending`, переход в `succeeded` при
     завершении заказа — этапы 8–9 (обходных API нет).
  2. **Попытка оплаты = строка `payments`, её `id` — `attempt_id`.**
     `POST /payments/mock/confirm` принимает `{order_id, attempt_id,
     outcome}`; только владелец заказа (чужой заказ или попытка — `404`).
     Заказ блокируется (`FOR UPDATE`), поэтому параллельные запросы
     выполняются по очереди. Для `pending`-попытки при заказе `pending` и
     `payment_due_at > now()`: `success` → попытка `succeeded`, `paid_at`,
     `payment_due_at = NULL` (заказ остаётся `pending` до персонала);
     `failure` → попытка `failed` и в той же транзакции новая `pending`
     с новым `transaction_reference`. Повтор с тем же `attempt_id` и тем
     же `outcome` возвращает сохранённый результат этой попытки без новых
     записей; новая попытка подтверждается только своим `attempt_id`.
     Повторный `success` для уже оплаченного заказа — `200` с текущим
     состоянием; иначе (не `mock_card`, заказ не `pending`, срок истёк,
     попытка уже завершена с другим результатом, `failure` после
     успешной оплаты) — `409 PAYMENT_NOT_ALLOWED`. Два `succeeded`
     невозможны (блокировка заказа и частичный UNIQUE).
  3. **Ответ confirm:** `order_id`, `order_status`, `payment_status`
     (статус последней попытки), `payment_due_at`, `attempt` (`id`,
     `status`, `transaction_reference`, `amount`, `currency`,
     `created_at`, `paid_at`) — состояние после транзакции.
  4. **Ядро единой операции отмены** (§14.3, DEC-39…DEC-41, DEC-82):
     блокирует заказ; уже `cancelled` — возврат без побочных эффектов;
     проверка перехода по таблице §7.1; `cancelled`, `cancelled_at`,
     причина, история с комментарием; платежи `succeeded` (mock) →
     `refunded` (`refunded_at`), `pending` → `cancelled`; активное
     назначение курьера → `cancelled`; `pending`-запрос отмены →
     `approved`; доменное событие — всё в одной транзакции. Сейчас его
     вызывает только таймаут; действия персонала (прямая отмена,
     одобрение и отклонение запросов, `rejected`) — этапы 8–9.
  5. **Таймаут оплаты в worker** (DEC-84, DEC-104, §14.5): каркас
     фоновых задач; задача раз в 60 с отменяет заказы `pending` с
     `payment_due_at < now()` пачками до 50, `FOR UPDATE SKIP LOCKED`,
     каждый заказ — в своей транзакции; ошибка одного заказа не
     останавливает задачу и worker; оплаченный заказ (`payment_due_at =
     NULL`) не трогается; повторная обработка ничего не меняет. Очистка
     `idempotency_keys` — этап 10 (DEC-148).
  6. **Без отдельного `GET /orders/{id}/payments`:** попытки и их
     статусы — в `payments[]` ответа `GET /orders/{id}` (только
     владелец). `GET /payment-methods` (публичный) возвращает активные
     способы. Экран демо-оплаты — `/orders/:id/pay`; после заказа с
     `mock_card` покупатель попадает на него.
  7. Проверка скрытия неоплаченных заказов из очереди персонала —
     этап 8; в этапе 7 проверяются `payment_due_at` и `PAYMENT_REQUIRED`.
  - DEC-01–DEC-148 не изменяются, кроме снятия DEC-148 п. 1.

- **DEC-151. Решения этапа 9 (курьеры и назначения)** (утверждено
  2026-11-13; по итогам аудита этапа 9, решения Р1–Р9):
  1. **Неудачная доставка (Р1, вариант А).** В v1 нет отдельного
     системного статуса или перехода для неудачной доставки, отказа
     клиента или возврата заказа. Из `out_for_delivery` возможен только
     переход в `completed` (DEC-30, DEC-33 не меняются); переназначение
     после `out_for_delivery` недоступно (DEC-48). Такие случаи
     администратор решает вне системы. Миграция не создаётся.
  2. **Лимит курьера (Р2).** Администратор меняет `max_active_orders`
     через `PATCH /admin/couriers/{user_id}/availability` (тело:
     необязательные `is_available` и `max_active_orders`, хотя бы одно
     поле); допустимый диапазон 1–10 проверяется API (`422
     VALIDATION_ERROR`), CHECK `max_active_orders > 0` в БД сохраняется.
     Уменьшение лимита ниже текущего числа активных назначений
     допускается: существующие назначения не снимаются, новые не
     выдаются, пока число активных не станет меньше лимита. Курьер
     сам меняет только `is_available` (`PATCH /courier/me/availability`).
  3. **Автоназначение (Р3, уточняет DEC-49).** Кандидат — пользователь
     с ролью `courier`, `is_active = true`, профилем `courier_profiles`
     с `is_available = true`, числом активных назначений меньше
     `max_active_orders` и без назначения `declined` на этот заказ
     (DEC-92). Порядок выбора, вычисляемый под блокировками п. 6:
     1) число активных назначений (`status = 'active'`) — по
        возрастанию;
     2) `last_assigned_at` = `max(assigned_at)` по **всем** назначениям
        курьера любого статуса — по возрастанию; курьер без назначений
        (`NULL`) идёт первым (`NULLS FIRST`);
     3) `user_id` — по возрастанию (порядок типа `uuid` в PostgreSQL).
     Выбирается первый кандидат; кандидатов нет — `409
     NO_COURIER_AVAILABLE` (DEC-50). Ручное назначение проверяет те же
     условия, кроме исключения отказавшихся (DEC-92), иначе `409
     COURIER_NOT_AVAILABLE`.
  4. **Повторные запросы (Р4).** Все действия курьера требуют, чтобы
     назначение принадлежало ему (иначе `404`, DEC-106):
     - повторный `accept` по своему активному принятому назначению —
       `200` без изменений (`accepted_at` не перезаписывается);
     - повторный `delivered` по своему назначению в статусе
       `completed` (заказ `completed`) — `200` с текущим состоянием, без
       повторных побочных эффектов (платёж, `delivered_at`, история,
       событие);
     - повторный `picked-up` — `409 INVALID_STATUS_TRANSITION` (заказ уже
       не в `ready_for_pickup`);
     - `assign-courier` того же курьера, у которого уже есть активное
       назначение на этот заказ, — `200` без изменений: новое назначение
       не создаётся, прежнее не отменяется, `assigned_by` и
       `assignment_type` не меняются. Проверка статуса заказа (DEC-48)
       выполняется раньше: вне `confirmed`…`ready_for_pickup` — `409
       INVALID_STATUS_TRANSITION`;
     - `auto-assign-courier` для заказа, у которого уже есть активное
       назначение (любого курьера), — `200` с текущим назначением, без
       изменений в БД: новое назначение не создаётся, текущее не
       отменяется, кандидаты не выбираются (закрывает Q-19 п. 1).
       Проверка типа и статуса заказа (DEC-48) выполняется раньше, как
       для `assign-courier`;
     - повторный `decline` по своему назначению, уже находящемуся в
       статусе `declined`, — `200` с текущим состоянием, без повторных
       побочных эффектов: `declined_at` и `decline_reason` не
       перезаписываются (закрывает Q-19 п. 2). Ответ на `decline`
       (первый и повторный) содержит только данные уровня истории, без
       адреса и контактов клиента (DEC-106);
     - заменить текущего курьера можно только ручным переназначением
       `assign-courier` другого курьера (DEC-51); автоназначение
       текущее назначение не заменяет.
  5. **Отказ курьера (Р5, дополняет DEC-92).** Отказ разрешён только
     пока назначение не принято **и** заказ не перешёл в
     `out_for_delivery`. После принятия — `409
     ASSIGNMENT_ALREADY_ACCEPTED`; если заказ уже `out_for_delivery`
     (например, после вмешательства администратора без принятия,
     DEC-91) — `409 INVALID_STATUS_TRANSITION`. Принять такое
     непринятое назначение тоже нельзя: `accept` после перехода заказа в
     `out_for_delivery` вмешательством администратора — `409
     INVALID_STATUS_TRANSITION`, `accepted_at` не заполняется (принятие
     возможно только до `out_for_delivery`, DEC-83; фиктивного принятия
     нет, DEC-91). Повторный `accept` по уже принятому назначению — по
     п. 4.
  6. **Порядок блокировок (Р6, уточняет DEC-67, совместим с DEC-140 и
     DEC-143).** Анализ кода этапов 3–8 (уровень изоляции READ
     COMMITTED, `app/db/session.py`):
     - фактические цепочки в коде: изменение статуса, единая отмена,
       кухня — `orders` (`FOR UPDATE`) → строки `payments`,
       `courier_assignments`, `cancellation_requests` → вставка
       `order_status_history`; рассмотрение запроса отмены — `orders` →
       `cancellation_requests`; mock-оплата — `orders` → `payments`;
       login, refresh, logout, смена и сброс пароля — `users` (`FOR NO
       KEY UPDATE`, `lock_user`, DEC-140, DEC-143) → `refresh_tokens`;
       сотрудники (роли, деактивация, реактивация, этап 8) — `users`
       (сейчас `FOR UPDATE`) → `user_roles` → вставка `courier_profiles`
       (`ON CONFLICT DO NOTHING`, без ожидания блокировки существующей
       строки) → `refresh_tokens`; никакая операция, удерживающая `users`
       или `courier_profiles`, не блокирует `orders`;
     - вставка в `courier_assignments`, `order_status_history` и
       `orders` неявно берёт `FOR KEY SHARE` на строку `users` (FK
       `courier_id`, `assigned_by`, `changed_by`, `user_id`); этот режим
       конфликтует только с `FOR UPDATE`;
     - **единый порядок (частичный):** `orders` → `users` →
       `courier_profiles` → `courier_assignments`; ветка DEC-140 `users →
       refresh_tokens` и `users → user_roles` с ним совместима (общий
       префикс `users`). Обратные порядки запрещены: удерживая `users`
       или `courier_profiles`, нельзя блокировать `orders`; удерживая
       `courier_profiles`, нельзя блокировать `users` (явно). Таблицы,
       не нужные операции, пропускаются;
     - **режим блокировки `users` в операциях сотрудников** приводится к
       `FOR NO KEY UPDATE`, как требует DEC-140 для деактивации (код
       этапа 8 использует `FOR UPDATE`; изменение входит в объём этапа
       9). Взаимоблокировки текущий режим не создаёт (операции
       сотрудников не ждут `orders` и `courier_profiles`), но лишне
       блокирует неявный `FOR KEY SHARE` при вставках заказов и истории;
     - **назначение и переназначение:** `orders` (`FOR UPDATE`) →
       `users` курьера (`FOR SHARE`, перепроверка роли `courier` и
       `is_active`) → `courier_profiles` (`FOR UPDATE`, перепроверка
       доступности и лимита) → прежнее активное назначение → `cancelled`
       → новое назначение. `FOR SHARE` (а не `FOR KEY SHARE`) выбран
       потому, что он конфликтует с `FOR NO KEY UPDATE` операций
       сотрудников и сериализует назначение с деактивацией и снятием
       роли;
     - **автоназначение:** `orders` → `users` всех кандидатов `FOR
       SHARE`, затем их `courier_profiles` `FOR UPDATE`, каждый раз
       одним запросом `ORDER BY user_id` по одному и тому же списку;
       число активных назначений пересчитывается под блокировками, затем
       применяется порядок п. 3. Ручное назначение блокирует не больше
       одного профиля, поэтому цикла с автоназначением нет;
     - **принятие, отказ, «забрал», «доставлен»:** `orders` (`FOR
       UPDATE`) → строка назначения; `users` и профиль явно не
       блокируются;
     - **доступность и лимит:** только `courier_profiles` (`FOR UPDATE`)
       одной строки; другие блокировки не берутся;
     - **деактивация курьера и снятие роли `courier`:** `users` (`FOR NO
       KEY UPDATE`) → проверка активных назначений (DEC-29, DEC-150).
       Блокировка конфликтует с `FOR SHARE` назначения, поэтому операции
       сериализуются: если первым завершилось назначение, проверка видит
       активное назначение (`409 COURIER_HAS_ACTIVE_ASSIGNMENTS`); если
       первой завершилась деактивация, назначение видит `is_active =
       false` (`409 COURIER_NOT_AVAILABLE`);
     - **отсутствие циклов:** ожидание возможно только «вперёд» по
       частичному порядку, а операции, удерживающие `users`
       (сотрудники, сессии) или `courier_profiles` (доступность), не
       ждут `orders`; поэтому цикл ожиданий невозможен;
     - конкурентные тесты обязательны: два назначения на лимит 1, два
       автоназначения разных заказов, назначение против деактивации,
       назначение против снятия роли, принятие против переназначения,
       отказ против переназначения, «доставлен» против отмены, без
       взаимоблокировок (`deadlock detected`) и с соблюдением
       инвариантов.
  7. **Клиент (Р7).** Имя и контакты курьера клиенту в v1 не
     показываются: в ответах клиентских API данных курьера нет.
  8. **Sandbox (Р8).** Для приёмки этапа 9 разрешено создать ровно
     одного тестового сотрудника с ролью `courier` через `POST
     /admin/staff` только в `food_delivery_sandbox`, после проверки
     фактического `current_database()`. Других сотрудников не создавать,
     администратора повторно не создавать (DEC-150 п. 9 для этапа 8 не

- **DEC-152. Уточнения этапа MA (Telegram Mini App)** (уточняет
  DEC-142, DEC-144, DEC-105; совместим с DEC-140, DEC-143 и DEC-151
  п. 6; утверждено 2026-11-13):
  1. **Маршруты.** Mini App работает на маршрутах с префиксом `/tg`:
     точка входа `/tg` и `/tg/menu`, `/tg/menu/:productId`, `/tg/cart`,
     `/tg/checkout`, `/tg/orders`, `/tg/orders/:orderId`,
     `/tg/orders/:orderId/pay`, `/tg/account`.
     - Страницы используют те же компоненты, что и сайт, но собственный
       макет: без шапки и подвала сайта, без ссылок входа, регистрации и
       выхода. Маршруты сайта не меняются; переходов между маршрутами
       сайта и Mini App нет.
     - Режим Mini App определяется только путём `/tg`. Открытие или
       перезагрузка любой страницы `/tg/*` заново выполняет обмен
       `init_data`. Если вход невозможен — экран «перезапустите Mini
       App»; страницы `/login` в Mini App нет.
     - Официальный скрипт SDK загружается только на `/tg` и `/tg/*`.
       nginx для `/tg` и `/tg/*` отдаёт `Content-Security-Policy:
       frame-ancestors https://web.telegram.org` без `X-Frame-Options`;
       для остальных адресов — `X-Frame-Options: DENY`.
  2. **Вход, регистрация и привязка.** Три публичные операции без cookie
     и CSRF; каждая выдаёт только access-токен (`{access_token,
     token_type, expires_in}`). Проверка `init_data` (DEC-142) всегда
     выполняется первой; пока бот не настроен — `409
     TELEGRAM_DISABLED`.
     1. `POST /auth/telegram/webapp {init_data}` — только вход. Связь
        `telegram_links.telegram_chat_id = user.id` найдена: проверяются
        `is_active` пользователя (неактивный — `401
        INVALID_TELEGRAM_AUTH`) и роль `customer` (нет — `403
        FORBIDDEN`), выдаётся токен. Связи нет — `409
        TELEGRAM_NOT_LINKED`, в БД ничего не меняется. Аккаунт
        автоматически не создаётся (заменяет DEC-142).
     2. `POST /auth/telegram/webapp/register {init_data}` — создание
        нового клиента. Одна транзакция: advisory-блокировка (п. 3),
        повторный поиск связи. Связи нет — создаются пользователь
        `customer` без email и пароля (имя — по DEC-142, язык — по п. 10
        этого решения), его роль и `telegram_links`. Связь есть — новый аккаунт не создаётся,
        результат — как в п. 2.1.
     3. `POST /auth/telegram/webapp/link {init_data, email, password}` —
        привязка существующего аккаунта сайта:
        - email и пароль проверяются как в `/auth/login`: аккаунт без
          email не находится; неизвестный email — фиктивная проверка
          пароля; неверный пароль и неактивный аккаунт — один и тот же
          `401 INVALID_CREDENTIALS`;
        - пароль верный, но у аккаунта нет роли `customer` — `403
          FORBIDDEN`;
        - одна транзакция: advisory-блокировка (п. 3) → `users` (`FOR NO
          KEY UPDATE`) с повторным чтением `is_active` и `password_hash`
          (изменились — `401 INVALID_CREDENTIALS`, как DEC-143) → **после**
          этой блокировки проверяются обе связи: этот Telegram связан с
          другим пользователем — `409 TELEGRAM_ALREADY_LINKED`; у
          пользователя есть связь с другим Telegram — `409
          ACCOUNT_ALREADY_LINKED`; та же пара — `200` без изменений;
          иначе вставляется `telegram_links` (`telegram_username`,
          `is_active` по п. 8, `linked_at`);
          *Уточнено DEC-154 пп. 3--5: «без изменений» для той же пары,
          `is_active`, `telegram_username`, повторная проверка роли под
          блокировкой `users`.*
        - ответ — токен этого аккаунта. Данные пользователя (`full_name`,
          `phone`, `preferred_language`, email, пароль) и его заказы не
          изменяются; при любой ошибке транзакция откатывается целиком.
     4. Связь создаётся только при доказанном владении обеими сторонами:
        Telegram — проверенным `init_data`, аккаунтом — паролем или
        одноразовым токеном сайта (этап 10, DEC-87). Сопоставление по
        имени, телефону или username Telegram не выполняется.
     5. Переноса связи (автоматического или ручного) и слияния
        аккаунтов в v1 нет. Нарушение `UNIQUE(user_id)` или
        `UNIQUE(telegram_chat_id)` даёт `409` по правилу п. 2.3 с полным
        откатом.
     6. Аккаунт только с Telegram может добавить email и пароль (`POST
        /auth/credentials`, без изменений) и входить на сайт; с другим
        аккаунтом сайта он не объединяется.
     7. `POST /telegram/link/webapp` (DEC-142) не реализуется.

- **DEC-153. Уточнения MA-1: `/users/me` и откат ревизии `0009`**
  (уточняет DEC-142 K2-B и DEC-152 п. 9; утверждено 2026-11-13):
  1. **Ответ `GET /users/me` и `PATCH /users/me`** — тот же, что у
     `GET /auth/me`: `id`, `email` (`null` у аккаунта только с
     Telegram), `full_name`, `phone`, `preferred_language`, `roles`,
     `must_change_password`, `has_password`; поля формируются по тем же
     правилам. `PATCH` отвечает `200` с профилем после изменения.
  2. **`PATCH /users/me`** изменяет только `full_name`, `phone` и
     `preferred_language` (DEC-152 п. 9); остальные поля (`email`,
     `password`, роли, флаги, `id`, `user_id` и любые другие) —
     `422 VALIDATION_ERROR` без изменений в БД. Правила полей — как при
     регистрации (DEC-141, DEC-89). Явный `phone: null` очищает телефон;
     `null` в `full_name` или `preferred_language` — `422`. Пустое тело

     профилем. Изменяется только профиль из access-токена; доступ — как
     у прочих защищённых маршрутов (при `must_change_password` —
     `403 PASSWORD_CHANGE_REQUIRED`, DEC-28).
  3. **Откат ревизии `0009`.** Если в `users` есть хотя бы один аккаунт
     только с Telegram (`email IS NULL`; по `ck_users_credentials_pair`
     тогда и `password_hash IS NULL`), downgrade останавливается с
     ошибкой до любых изменений: данные пользователей не удаляются и не
     изменяются, схема и ревизия остаются прежними. Если таких

     и восстанавливает NOT NULL у `email` и `password_hash`.

- **DEC-154. Решения MA-2: проверка `init_data`, `telegram_links`,
  роль, лимиты, окружение** (уточняет DEC-142 и DEC-152 пп. 2, 4, 6, 8,
  12; совместим с DEC-153; утверждено 2026-11-14):
  1. **Пределы `init_data`.** Длина строки `init_data` — не более 4096
     символов (`TELEGRAM_WEBAPP_INIT_DATA_MAX_LENGTH`, по умолчанию
     4096). `auth_date` может опережать время сервера не более чем на 60
     секунд (`TELEGRAM_WEBAPP_CLOCK_SKEW_SECONDS`, по умолчанию 60);
     возраст — не более `TELEGRAM_WEBAPP_AUTH_MAX_AGE_SECONDS` (по
     умолчанию 3600, DEC-142). Все три значения задаются в конфигурации.
     *Уточнено DEC-155 п. 3: превышение длины — `401`, не `422`.*
  2. **Алгоритм подписи** — официальная проверка Telegram WebApp по
     токену бота (HMAC-SHA256):
     - строка проверки — все полученные поля, кроме `hash`, в виде
       `key=value`, отсортированные по ключу и соединённые символом
       `\n`; значения берутся после URL-декодирования;
     - поле `signature`, если оно есть, остаётся в строке проверки как
       обычное поле и не исключается;
     - секретный ключ — `HMAC-SHA256(key="WebAppData", msg=<токен
       бота>)`; подпись — `hex(HMAC-SHA256(key=<секретный ключ>,
       msg=<строка проверки>))`; сравнение с `hash` — за постоянное
       время (`hmac.compare_digest`);
     - отдельная проверка Ed25519 для сторонних сервисов (по полю
       `signature` и публичному ключу Telegram) в v1 не используется и
       с этим алгоритмом не смешивается.
     Ошибка любого шага — `401 INVALID_TELEGRAM_AUTH` без указания
     причины (DEC-142).
  3. **`telegram_links.is_active`** (уточняет DEC-152 п. 8) — только
     разрешение боту писать пользователю, не признак связи. Отсутствие
     поля `allows_write_to_pm` в проверенном `init_data` равносильно
     `false`:
     - новая связь (`register`, `link`): `is_active = TRUE`, если в
       проверенном `init_data` `allows_write_to_pm = true`, иначе
       `FALSE`;
     - успешный вход (`/auth/telegram/webapp`, а также `register` при
       уже существующей связи) и повторный `link` той же пары: при
       `allows_write_to_pm = true` устанавливается `TRUE`; при `false`
       или отсутствии поля существующее значение не меняется;
     - «та же пара — `200` без изменений» (DEC-152 п. 2.3) означает,
       что не меняются связь (`user_id`, `telegram_chat_id`),
       `telegram_username`, `linked_at` и данные пользователя;
       `is_active` меняется только по этому пункту.
  4. **`telegram_username`** записывается из проверенного `init_data`
     только при создании связи. При входе и повторном `link` той же пары
     не меняется; иное — отдельным решением.
     *Уточнено DEC-155 п. 2: не строка — отказ, длиннее 100 — NULL.*
  5. **Роль `customer` в `link`** (уточняет DEC-152 п. 2.3): первая
     проверка — после проверки пароля, до транзакции (`403 FORBIDDEN`);
     повторная — в транзакции после блокировки строки `users` (`FOR NO
     KEY UPDATE`). Роли нет на момент повторной проверки — `403
     FORBIDDEN` и полный откат транзакции.
  6. **Лимиты** (уточняет DEC-152 п. 4): `POST /auth/telegram/webapp` и
     `POST /auth/telegram/webapp/register` — общий отдельный счётчик
     `RATE_LIMIT_TELEGRAM_WEBAPP` (по умолчанию `5/minute`, по IP);
     `POST /auth/telegram/webapp/link` — общий с `/auth/login` счётчик
     `RATE_LIMIT_LOGIN`. Счётчик увеличивается до любой проверки.
  7. **Язык.** `language_code` сравнивается строго с `ru`, `ky`, `uz`;
     любое другое значение (в том числе `ru-RU`, `uz-Latn`, `en`) и
     отсутствие поля — `ru` (DEC-152 п. 10).
  8. **Окружение и инфраструктура.** В `.env.example` и `compose.yaml`

     `TELEGRAM_WEBAPP_AUTH_MAX_AGE_SECONDS`,
     `TELEGRAM_WEBAPP_INIT_DATA_MAX_LENGTH`,
     `TELEGRAM_WEBAPP_CLOCK_SKEW_SECONDS`, `RATE_LIMIT_TELEGRAM_WEBAPP`)
     без настоящих значений и токенов; пустой `TELEGRAM_BOT_TOKEN` —
     `409 TELEGRAM_DISABLED`. Автотесты используют только тестовый токен,
     заданный в тестах. Dockerfile, заголовки прокси и настройки прокси в
     Compose в MA-2 не меняются; ограничение определения IP клиента за

  9. **Тестовая БД MA-2** (уточняет DEC-152 п. 12): автотесты MA-2 —

- **DEC-155. Решения реализации MA-2: таймаут блокировок, username,
  длина `init_data`** (уточняет DEC-152 п. 3 и DEC-154 пп. 1, 4;

  1. **Таймаут блокировок (U1).** Транзакции `register` и `link` первой
     командой выполняют `SET LOCAL lock_timeout = '5s'`: ожидание любой
     блокировки (advisory, строки `users`, `telegram_links`) не дольше
     5 секунд. Только SQLSTATE `55P03` (`lock_not_available`) даёт полный

     `/auth/telegram/webapp` (вход) `lock_timeout` не задают.
  2. **`telegram_username` (U2).** Поле отсутствует — NULL; не строка —
     `init_data` отклоняется (`401 INVALID_TELEGRAM_AUTH`); строка
     длиннее 100 символов (или пустая) — NULL, без ошибки БД. Значение
     записывается только при создании связи (DEC-154 п. 4). Пустое имя
     заменяется на `username` только если он сохранился.
  3. **Длина `init_data` (D5).** Не более 4096 символов; превышение —
     `401 INVALID_TELEGRAM_AUTH`, а не `422`: у поля `init_data` в схеме
     запроса нет ограничения длины, вся проверка — в верификаторе.
     Причина отказа и входные данные не раскрываются.
  4. **Вход и `is_active`** (уточняет DEC-152 п. 3). Повышение
     `telegram_links.is_active` при входе — `UPDATE` одной строки
     `telegram_links` без advisory-блокировки и без блокировки `users`:
     связь при этом не создаётся и не удаляется, поэтому порядок DEC-152
     п. 3 не нарушается.
  - DEC-01–DEC-154 не изменяются, кроме уточнений DEC-152 п. 3 и DEC-154
    пп. 1, 4.

- **DEC-158. Постоянное хранение sandbox-режима (БД и изображения)**
  (уточняет DEC-145 п. 2; **предлагается к утверждению**, ред. 41):
  1. **БД.** Кластер `db-sandbox` (БД `food_delivery_sandbox`) хранится в
     именованном томе `db-sandbox-data` (Docker:
     `food-delivery_db-sandbox-data`), смонтированном строго в
     `/var/lib/postgresql/data` — PGDATA образа `postgis/postgis`.
     `tmpfs` для данных больше не используется: данные переживают
     остановку и пересоздание контейнера. Порт по-прежнему не
     публикуется.
  2. **Изображения.** Каталог `/app/media` backend в sandbox-режиме — в
     отдельном именованном томе `media-sandbox-data` (Docker:
     `food-delivery_media-sandbox-data`). Он заменяет том `media-data` из
     `compose.yaml` в той же точке монтирования; тома основного стека
     (`db-data`, `media-data`) в sandbox-режиме не используются и с
     sandbox-томами не смешиваются. worker файлы изображений не использует
     и тома не получает.
  3. **Удаление.** `docker compose down -v` и удаление sandbox-томов —
     только по отдельному разрешению: команда уничтожает данные и
     изображения sandbox.
  4. **Резервные копии.** БД (`pg_dump -Fc` и `-Fp`) и том изображений
     копируются вместе и вне репозитория (с SHA-256); восстановление —
     только по отдельному разрешению, после проверки `current_database()`.
     Копия БД без копии изображений даёт битые ссылки `image_path`.
  5. **Права доступа к `/app/media`.**
     - Sandbox использует dev-образ backend (стадия `dev`), контейнер
       работает от root (UID 0). Новый том `media-sandbox-data` создаётся
       с владельцем `root:root`; каталоги и файлы, которые пишет backend,
       тоже принадлежат root.
     - Production-образ (стадия `prod`, demo) запускается от пользователя
       `app` (UID 10001) и создаёт `/app/media` с владельцем `app`.
     - Том, заполненный dev-контейнером, может оказаться недоступным для
       записи production-пользователю: чтение возможно, загрузка
       изображений — нет.
     - Перед переходом на production выполняется контролируемый
       `chown -R 10001:10001` тома (по отдельному разрешению, с резервной
       копией) либо используется новый пустой том с корректно собранным
       production-образом, в котором `/app/media` принадлежит `app`.
  6. **Следствия.** Объём тома не ограничен (прежний `tmpfs` — 256 МиБ;
     каждый файл — до 5 МБ, DEC-70). Тестовые БД этапов, создаваемые в
     кластере `db-sandbox` (DEC-152 п. 12), теперь тоже сохраняются между
     перезапусками; их создание и удаление — по отдельному разрешению.
  7. **Связь с DEC-145.** После утверждения фраза DEC-145 п. 2 «В
     sandbox-режиме каталог — `tmpfs`» заменяется на «В sandbox-режиме
     каталог — отдельный том `media-sandbox-data` (DEC-158)»; до
     утверждения текст DEC-145 не меняется.
  - Статусы DEC-01–DEC-157 не изменяются.

- **DEC-159. Временная публикация sandbox и ручная проверка Mini App в
  Telegram до MA-5** (уточняет порядок применения DEC-142 (K3-C) и
  DEC-156 п. 6; **утверждено** 2026-11-19, ред. 42):
  1. **Вступление в силу.** Решение действует с даты его утверждения
     владельцем. До утверждения оно не является основанием для каких-либо
     действий.
  2. **Предшествующие факты.** Начиная с 2026-11-18 владелец в рабочем
     порядке отдельными разрешениями допустил временную публикацию
     sandbox-стенда через Quick Tunnel и ручную проверку сайта и Mini App
     в Telegram, в том числе 2026-11-19 — после публикации сборки MA-4.2.
     Эти действия фиксируются как факты; настоящее решение не даёт им
     ретроактивного разрешения и не изменяет их оценку. Дата 2026-11-18 —
     дата начала фактического использования, а не дата вступления
     решения в силу (п. 1).
  3. **Назначение.** Порядок временной публикации sandbox для ручной
     проверки на реальных клиентах (DEC-142, K3-C). Не заменяет хостинг
     с доменом и сертификатом (K3-D, этап 11) и задачи MA-5.
  4. **Среда.** Только sandbox: backend в sandbox-режиме и БД
     `food_delivery_sandbox` в `db-sandbox`. Хранение изображений —
     согласно DEC-145 п. 2; постоянное хранение данных и изображений
     sandbox — предмет DEC-158. Ссылка на DEC-158 не означает его
     утверждения и не меняет его текущий статус. Основная БД
     `food_delivery`, её тома и production-окружение не используются и не
     изменяются. Автотесты — по DEC-152 п. 12.
  5. **Сборка.** Сайт и Mini App отдаются из одной согласованной
     production-сборки frontend (сборки для production-режима) на одном
     origin; это не означает использования production-окружения.
     Публикация новой сборки — только с отдельного разрешения, с
     резервной копией текущей сборки, контрольными суммами, проверкой
     результата и возможностью отката. Demo-контейнер этим решением не
     собирается (MA-5).
  6. **Обратный прокси.** Перед приложением работает отдельный nginx:
     - он — единственная точка входа извне; порты приложения и БД на хосте
       не публикуются;
     - пропускает к backend только согласованный набор маршрутов API,
       остальные запросы отклоняет;
     - конфигурация и сборка для него доступны только для чтения;
     - изменение конфигурации и переключение на другую её версию — только
       с отдельного разрешения, с возможностью отката.
     Способ запуска, расположение файлов, контрольные суммы и процедуры
     переключения — оперативные материалы P2.x вне репозитория; они
     требованиями этого решения не являются.
  7. **Доступ и адрес клиента.**
     - Цепочка: клиент → Cloudflare → временный Quick Tunnel → nginx →
       backend. Адрес туннеля временный и меняется при перезапуске.
     - nginx доверяет заголовку `CF-Connecting-IP` только для соединений
       от одного точно заданного сетевого адреса коннектора туннеля (не
       диапазона); для остальных соединений адрес клиента — адрес самого
       соединения. Значение заголовка должно быть ровно одним адресом,
       иначе запрос отклоняется.
     - Заголовки адреса, присланные клиентом (`X-Forwarded-For`,
       `X-Real-IP` и аналогичные), не учитываются при определении адреса;
       к backend они передаются заменёнными значением, определённым nginx,
       либо пустыми.
     - Доступ разрешён только с IP-адресов из списка владельца; список
       применяется к адресу, определённому по правилам выше; пустой список
       запрещает доступ всем.
     - Доверие к `CF-Connecting-IP` основано на предположении, что
       значение, подставленное клиентом, не передаётся через Cloudflare и
       туннель до nginx. Проверки P2.6 от 2026-11-18 и 2026-11-19 показали
       лишь, что в этих запусках запрос с подставленным значением был
       отклонён до nginx: ответ не содержал проверяемого заголовка nginx,
       подставленный адрес отсутствовал в журнале nginx. Точное место
       отклонения и постоянство этого поведения не установлены;
       документация Cloudflare в рамках проверки не изучалась.
     - Поэтому такая проверка повторяется при каждом включении или
       возобновлении публикации, а также после изменения конфигурации
       nginx или туннеля. Она признаётся пройденной, только если ответ не
       сформирован nginx и подставленный адрес не появился в его журнале;
       при неуспешной проверке публикация останавливается. Проверка
       подтверждает наблюдаемое поведение в момент проверки и не
       гарантирует постоянную защиту.
     - Адрес туннеля, IP-адреса и списки доступа в репозиторий не
       записываются. Определение IP клиента в backend за прокси остаётся
       известным риском (DEC-154 п. 8); настоящее решение этот риск не
       устраняет и не меняет.
  8. **Backend и секреты.** Публичный origin туннеля задаётся backend в
     `CSRF_TRUSTED_ORIGINS` (DEC-142, K3) и в `FRONTEND_BASE_URL` — только
     на время публикации и только для sandbox. Токен бота и другие
     секреты передаются только через окружение; они не записываются в
     репозиторий, журналы, отчёты и документацию, не выводятся в консоль
     и не попадают в сборку frontend. Конкретный способ передачи
     определяется при каждом применении; изменение файлов окружения и
     Compose — только с отдельного разрешения.
  9. **Ручная проверка в Telegram.** На устройстве допускается до
     завершения MA-5 — только с отдельного разрешения владельца и только
     в среде по пп. 4–8. Кнопку Mini App в BotFather настраивает владелец
     вручную (DEC-152 п. 6). Проверка в Telegram Web во фрейме — после
     MA-5. Онлайн-оплата — только `mock_card` (DEC-149); реальные
     онлайн-платёжные операции запрещены. Наличный способ оплаты,
     предусмотренный DEC-149, этим решением не запрещается.
  10. **Заголовки фрейма (K4-B).**
      - Целевые требования DEC-142 (K4-B) и DEC-152 п. 1 действуют без
        изменений и обязательны после MA-5; это решение их не ослабляет.
      - Только для sandbox и только до завершения MA-5 допускается
        временная неполная защита от встраивания во фрейм — исключительно
        для ограниченной ручной проверки по п. 9, с осознанием риска
        clickjacking.
      - Список IP (п. 7) ограничивает круг тех, кто может обращаться к
        sandbox, но защитой от clickjacking не является: встроенная во
        фрейм страница загружается браузером разрешённого пользователя с
        его адреса.
      - Отклонение не распространяется на другие среды и закрывается в
        MA-5 переключением конфигурации nginx — по отдельному разрешению.
  11. **Не разрешается этим решением:** изменения production-окружения и
      основной БД; реальные платежи; очистка и удаление данных и томов
      sandbox (DEC-158 п. 3); переключение nginx на новую версию
      конфигурации, в том числе MA-5; постоянная публикация и домен
      (этап 11); раскрытие секретов.
  12. **Завершение и перезапуск.** Публикация временная; её остановка —
      по решению владельца. После перезапуска туннеля новый origin
      задаётся backend по п. 8 с отдельного разрешения; адрес в BotFather
      обновляет владелец.
  13. **Связь с другими решениями.** Решение уточняет порядок применения
      DEC-142 (K3-C) и DEC-156 п. 6 начиная с даты утверждения; тексты
      DEC-142 и DEC-156 не переписываются, к ним добавляются пометки
      «Уточнено DEC-159». С даты утверждения DEC-156 п. 6 применяется
      так: ручная проверка в Telegram на устройстве — в sandbox по
      DEC-159, до MA-5 только с отдельного разрешения владельца; проверка
      во фрейме Telegram Web — после MA-5. Для периода до утверждения
      действует п. 2. Статус DEC-158 этим решением не меняется.
